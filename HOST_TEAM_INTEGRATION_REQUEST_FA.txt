درخواست اطلاعات و قراردادهای اتصال ماژول مالی به داشبورد اصلی BAMBO
=================================================================

مخاطب: تیم توسعه داشبورد اصلی و بکند BAMBO

هدف
----
ماژول مالی قرار است داخل محتوای داشبورد اصلی نمایش داده شود و هدر، سایدبار، احراز هویت و انتخاب پروژه مستقل نداشته باشد. اطلاعات باید متعلق به همان سازمان و پروژه‌ای باشند که کاربر در هدر انتخاب کرده است.
هدف این درخواست، استفاده از زیرساخت مشترک سایت و جلوگیری از ساخت سیستم موازی برای Context، دسترسی، دریافت داده، چاپ و اجزای رابط کاربری است.
لطفاً پاسخ‌ها را با شماره بخش مربوط، نمونه کد، قرارداد API یا مسیر فایل ارائه کنید. برای قابلیت موجودنبودن نیز صریحاً مشخص کنید که نیازمند توسعه است و مسئول آن کدام تیم خواهد بود.

۱. پروژه و سازمان انتخاب‌شده در هدر — ضروری
-------------------------------------------
- منبع معتبر پروژه و سازمان فعال چیست؟ Store، تابع عمومی، Context یا پارامتر URL؟
- ماژول هنگام شروع کار چگونه projectId و organizationId را دریافت کند؟
- هنگام تغییر انتخاب در هدر، چه رویداد یا Subscriptionای منتشر می‌شود؟ نام و نمونه Payload آن چیست؟
- آیا سازمان و پروژه با هم در یک رویداد نهایی اعلام می‌شوند یا جداگانه؟
- هنگام تغییر سازمان، پروژه قبلی چه زمانی پاک یا جایگزین می‌شود؟
- در حالت «هیچ پروژه‌ای انتخاب نشده» یا «همه پروژه‌ها»، رفتار موردانتظار ماژول مالی چیست؟
- آیا انتخاب فعال پس از Refresh حفظ می‌شود؟ مسئول بازیابی آن کدام بخش است؟
- شناسه پروژه باید به شکل رشته استفاده شود؟ نمونه‌های موجود مانند project و terrace شناسه معتبر هستند؛ آیا محدودیت دیگری وجود دارد؟

خروجی موردنیاز: نمونه کد خواندن انتخاب فعلی، گوش‌دادن به تغییر انتخاب و لغو Subscription.

۲. اطلاعات پایه پروژه و مسیرهای API — ضروری
-------------------------------------------
- مسیر رسمی دریافت جزئیات یک پروژه چیست؟
- مسیر دریافت پروژه‌های قابل‌دسترسی هر سازمان چیست؟
- چرا درخواست جزئیات پروژه‌ای که در /api/projects وجود دارد ممکن است 404 بدهد؟ مسیر یا مجوز خاصی لازم دارد؟
- رابطه پروژه با سازمان از کدام پاسخ دریافت می‌شود؟
- کدام فیلدها برای نام، کد، وضعیت، زیربنا و لوگوی پروژه/سازمان معتبر هستند؟
- وضعیت پروژه آرشیوشده چه اثری روی مشاهده و ویرایش اطلاعات مالی دارد؟

خروجی موردنیاز: نمونه پاسخ موفق جزئیات یک پروژه، فهرست پروژه‌های یک سازمان و نمونه خطای عدم دسترسی.

۳. کاربر، ورود و مجوزها — ضروری
-------------------------------
نمونه‌هایی از /api/me و /api/rbac/my-permissions در اختیار داریم، اما موارد زیر باید روشن شوند:

- درخواست‌های ماژول باید از کلاینت API عمومی سایت استفاده کنند؟ مسیر فایل و روش استفاده چیست؟
- ورود بر پایه Cookie است یا Bearer Token؟ ماژول نباید سیستم ورود جداگانه بسازد.
- اگر نشست منقضی شود، چه بخشی Refresh یا هدایت به ورود را انجام می‌دهد؟
- برای درخواست‌های تغییردهنده، CSRF یا هدر دیگری لازم است؟
- مجوزها سراسری‌اند یا برای پروژه و سازمان انتخاب‌شده تغییر می‌کنند؟
- بعد از تعویض پروژه، مجوزها چگونه به‌روز می‌شوند؟
- نگاشت رسمی مجوزهای مالی برای عملیات زیر چیست؟
  * مشاهده اطلاعات مالی
  * ویرایش اطلاعات مالی
  * مشاهده گزارش
  * ثبت گزارش تغییرناپذیر
  * دریافت خروجی گزارش
- رفتار رسمی isBamboAdmin چیست؟ آیا مجوزها باید صریحاً بررسی شوند؟

خروجی موردنیاز: کلاینت API عمومی، روش دریافت مجوز پروژه فعال و نمونه پاسخ برای کاربر مشاهده‌گر و ویرایشگر.
نکته امنیتی: نیازی به ارسال توکن، Cookie، رمز یا اطلاعات محرمانه نیست. نمونه‌ها را با داده غیرحساس ارسال کنید.

۴. قرارداد API مالی و محدوده پروژه — ضروری
------------------------------------------
- APIهای مالی با چه پیشوندی روی سایت اصلی منتشر می‌شوند؟
- آیا مسیرها زیر همان دامنه داشبورد هستند یا سرویس جدا دارند؟
- بکند سازمان را از پروژه و نشست کاربر تشخیص می‌دهد یا هدر مشخصی لازم دارد؟
- نسخه معتبر قرارداد مالی کدام است؟ لطفاً OpenAPI یا مستندات فعلی را ارائه کنید.
- آیا تمام مسیرهای مربوط به بخش‌های زیر برای پروژه انتخاب‌شده پشتیبانی می‌شوند؟
  * تنظیمات مالی و زیربنا
  * اقلام، فعالیت‌ها و ردیف‌های برآورد
  * قیمت‌ها و قواعد تبدیل واحد
  * پیشرفت و مقادیر انجام‌شده
  * فاکتورها و چرخه تأیید، ابطال و اصلاح
  * ورود گروهی و فایل‌ها
  * نمای کلی، گزارش زنده، ماهانه و سطح ۱
  * گزارش‌های ثبت‌شده
  * تاریخچه و ممیزی
- قالب استاندارد خطا، صفحه‌بندی، مرتب‌سازی و فیلتر تاریخ چیست؟

خروجی موردنیاز: قرارداد معتبر و آدرس محیط تست API مالی.

۵. مالکیت داده و منبع معتبر اعداد — ضروری
----------------------------------------
لطفاً مشخص کنید هر داده متعلق به سایت اصلی است یا ماژول مالی، کدام بخش مجاز به تغییر آن است و روش همگام‌سازی چیست:

- زیربنا: زیربنای پروژه اصلی یا آخرین بازنگری مالی؟ تغییر چگونه همگام می‌شود؟
- برآورد اولیه: مبلغ دستی پروژه اصلی یا مجموع ردیف‌های برآورد مالی؟
- هزینه واقعی: مبلغ دستی پروژه اصلی یا مجموع اسناد مالی مؤثر؟
- فعالیت‌ها و WBS: منبع MSP، فهرست فعالیت‌های میزبان یا فعالیت‌های مالی؟
- واحدها و اقلام: سراسری، سازمانی یا اختصاصی پروژه؟
- نام، کد و لوگو: مرجع معتبر برای نمایش و چاپ چیست؟

در پاسخ پروژه‌های فعلی، فیلدهای estimatedCost، actualCostToDate، costSource و costUnit دیده شده‌اند. لطفاً مشخص کنید بعد از فعال‌شدن ماژول مالی، این فیلدها چگونه با محاسبات مالی هماهنگ می‌شوند تا دو عدد متفاوت به کاربر نمایش داده نشود.
همچنین تأیید کنید مبالغ API به ریال هستند و نمایش ریال/تومان صرفاً در لایه نمایش انجام می‌شود.

۶. اتصال پیشرفت و MSP — ضروری برای محاسبات
------------------------------------------
- مسیر رسمی دریافت Snapshotهای پیشرفت پروژه چیست؟
- «آخرین Snapshot قابل استفاده» چگونه مشخص می‌شود؟
- تفاوت و نگاشت شناسه Snapshot میزبان و شناسه مالی چیست؟
- اتصال ردیف برآورد به فعالیت یا تخصیص منبع با کدام شناسه پایدار انجام می‌شود؟
- مقدار انجام‌شده از کدام فیلد خوانده می‌شود؟ مقدار واقعی، درصد پیشرفت یا ساعت کار؟
- پس از بارگذاری فایل جدید MSP، شناسه فعالیت‌ها و تخصیص‌ها پایدار می‌مانند؟
- حذف یا تغییر فعالیت چگونه اعلام می‌شود؟
- نبود پیشرفت یا نگاشت نامعتبر چه پاسخ و وضعیت کیفی دارد؟
- پس از ثبت Snapshot جدید، آیا رویدادی برای به‌روزرسانی ماژول مالی منتشر می‌شود؟

خروجی موردنیاز: نمونه Snapshot، فعالیت و تخصیص منبع، همراه توضیح شناسه‌ها و واحد مقادیر.

۷. محل نصب و چرخه عمر ماژول — ضروری
-----------------------------------
- ماژول چگونه در صفحه میزبان بارگذاری می‌شود؟ ES Module، قالب HTML، iframe یا روش دیگر؟
- شناسه یا قرارداد Container محتوای مالی چیست؟
- روش ورود و خروج از صفحه چیست؟ آیا قرارداد mount و unmount وجود دارد؟
- Router اصلی از Path یا Hash استفاده می‌کند؟ مسیرهای داخلی مالی باید چگونه ثبت شوند؟
- آیا لینک مستقیم به فاکتور یا گزارش یک پروژه پشتیبانی می‌شود؟
- مسئول پاک‌کردن Listenerها، بستن Dialogها و لغو درخواست‌های قبلی هنگام خروج یا تغییر پروژه کدام بخش است؟
- هنگام تغییر پروژه با فرم ذخیره‌نشده، تأیید کاربر را میزبان می‌گیرد یا ماژول؟

خروجی موردنیاز: یک صفحه نمونه واقعی که از هدر، پروژه فعال و Router مشترک استفاده می‌کند.

۸. فایل، Excel، OCR و Voice
---------------------------
- مسیر و محدودیت آپلود فایل چیست؟ حجم، فرمت و تعداد مجاز؟
- دانلود پیوست‌ها با URL موقت انجام می‌شود یا درخواست احرازهویت‌شده؟
- فایل چگونه به پروژه و فاکتور مرتبط می‌شود؟
- نتیجه پردازش Excel/OCR/Voice با Polling، SSE یا WebSocket اعلام می‌شود؟
- ساختار وضعیت Job، خطا، Retry و نتیجه چیست؟
- سرویس‌های OCR و Voice در محیط تست فعال‌اند؟
- قالب‌های رسمی Excel و فایل نمونه معتبر کدام‌اند؟

خروجی موردنیاز: نمونه چرخه کامل «آپلود ← پردازش ← بررسی کاربر ← ثبت نهایی».
استخراج خودکار نباید پیش از تأیید انسانی اثر مالی داشته باشد.

۹. چاپ، PDF و خروجی مشترک
-------------------------
- PDFهای سایت اصلی در کجا تولید می‌شوند و قالب مشترک آن‌ها کجاست؟
- آیا قالب گزارش‌های MSP برای داده مالی قابل استفاده است؟
- آیا سرویس تولید گزارش قرارداد عمومی دارد یا endpoint جداگانه مالی لازم است؟
- هدر، لوگو، فونت، شماره صفحه و جدول‌های ادامه‌دار چگونه تعریف می‌شوند؟
- روش رسمی دانلود فایل و نام‌گذاری آن چیست؟
- خروجی برای داده زنده ساخته می‌شود یا از گزارش ثبت‌شده و ثابت؟
- آیا گزارش‌ساز اصلی فهرست بخش‌های قابل انتخاب یا قرارداد افزونه‌ای دارد که شش پیشنهاد مالی به آن معرفی شوند؟

نمونه درخواست مشاهده‌شده در سایت اصلی:
https://dash.bambo.one/api/projects/project/msp/reports/complete.pdf?actual_snapshot=32&target_snapshot=1&previous_snapshot=13&sections=overview

این آدرس صرفاً نمونه گزارش MSP است و به معنی پشتیبانی آن از گزارش مالی نیست. لطفاً محل پیاده‌سازی و نحوه استفاده مجدد از بخش‌های عمومی آن را مشخص کنید.

شش پیشنهاد فعلی گزارش‌ساز مالی:
۱) خلاصه وضعیت مالی پروژه
۲) ترکیب هزینه
۳) گزارش مالی سطح ۱ با جزئیات
۴) منحنی S مالی
۵) کیفیت داده و محاسبات
۶) فاکتورها و اسناد مالی

خروجی موردنیاز: نمونه فراخوانی دانلود، قرارداد تولید PDF و روش استفاده از قالب مشترک.

۱۰. استایل‌ها و اجزای مشترک داشبورد
----------------------------------
- فایل اصلی Design Tokenها، فونت و تم روشن/تیره چیست؟
- تغییر تم چگونه به ماژول اعلام می‌شود؟
- Tooltip، Toast، Dialog، Date Picker و Loading عمومی چه API یا قواعدی دارند؟
- آیا Tooltipها برای عناصر جدیدی که بعداً به DOM اضافه می‌شوند هم فعال می‌شوند؟
- قواعد عمومی z-index و محل نمایش Overlayها چیست؟
- کدام کلاس‌ها یا استایل‌های سراسری روی محتوای ماژول اثر می‌گذارند؟
- آیا محدودیتی برای بارگذاری CSS، فونت، SVG یا CSP وجود دارد؟

خروجی موردنیاز: فایل ورودی استایل‌ها و یک نمونه استفاده از اجزای مشترک؛ نه لزوماً کل سورس داشبورد.

۱۱. تازه‌سازی و همگامی اطلاعات
-----------------------------
- تغییر داده توسط کاربر دیگر چگونه به ماژول اعلام می‌شود؟
- بعد از ثبت فاکتور، قیمت یا پیشرفت، کدام Cacheها باید باطل شوند؟
- آیا رویداد مشترکی برای تغییر اطلاعات مالی وجود دارد؟
- کنترل ویرایش هم‌زمان با version، ETag یا روش دیگری انجام می‌شود؟
- قرارداد جلوگیری از ثبت تکراری درخواست چیست؟

هدف این است که پاسخ دیررس پروژه قبلی یا داده Cacheشده در پروژه جدید نمایش داده نشود.

۱۲. محیط تست و تحویل نهایی — ضروری
----------------------------------
- آدرس محیط Staging و نسخه API قابل تست چیست؟
- دو پروژه آزمایشی با داده‌های متفاوت برای تست جداسازی پروژه‌ها می‌خواهیم.
- دسترسی تست مشاهده‌گر و ویرایشگر چگونه فراهم می‌شود؟
- ثبت و ابطال اسناد آزمایشی در آن محیط مجاز است؟
- برای پیگیری خطا، requestId و لاگ‌ها را به چه کسی تحویل دهیم؟
- روش انتشار فایل‌های ماژول، نسخه‌بندی و بازگشت نسخه چیست؟

دسترسی مستقیم به دیتابیس اصلی لازم نیست؛ API مستند و محیط تست کافی است.

اولویت دریافت اطلاعات
----------------------
برای شروع اتصال، این پنج مورد بالاترین اولویت را دارند:
۱) کد دریافت پروژه/سازمان فعال و رویداد تغییر آن
۲) کلاینت API و مجوزهای پروژه فعال
۳) قرارداد معتبر API مالی و اطلاعات پایه پروژه
۴) نمونه صفحه میزبان و روش نصب ماژول
۵) محیط تست با دو پروژه متفاوت

قرارداد پیشرفت/MSP نیز پیش از تأیید محاسبات وابسته به پیشرفت ضروری است. اطلاعات زیرساخت مشترک PDF برای یکپارچه‌سازی چاپ دریافت خواهد شد. ابتدا اتصال و جداسازی درست داده‌ها قطعی می‌شود و سپس قالب‌ها و امکانات مشترک یکپارچه می‌شوند.

قالب پیشنهادی پاسخ تیم اصلی
---------------------------
برای هر بخش لطفاً این موارد را اعلام کنید:
- وضعیت: موجود / نیازمند توسعه / نامرتبط
- مسئول یا تیم پاسخ‌گو
- فایل، تابع، رویداد یا endpoint رسمی
- قرارداد ورودی و خروجی و نمونه غیرحساس
- مجوز و پیش‌نیاز استفاده
- روش آزمایش در محیط تست
- محدودیت‌ها و موارد تصمیم‌گیری‌نشده

تا مشخص‌شدن قراردادها، از ارسال اطلاعات محرمانه، تغییر داده‌های واقعی و فرض‌کردن رفتار تعریف‌نشده خودداری می‌کنیم.
