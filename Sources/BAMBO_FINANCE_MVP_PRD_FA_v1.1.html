۲. زمینه محصول و مسئله

بامبو پلتفرم پایش پروژه ساختمانی برای مالک، سازمان و تیم پروژه است. ماژول مالی باید ستون «پول روی واقعیت» را به دو ستون موجود واقعیت پروژه و کنترل پروژه متصل کند: مقدارهای متره و برنامه از MSP/ورودی دستی، پیشرفت و مصرف از Snapshot گزارش پیشرفت، هزینه واقعی از فاکتورهای تأییدشده و هزینه باقی‌مانده از قیمت روز.

مسئله اصلی

  • مالک معمولاً برآورد اولیه، هزینه واقعی، ارزش روز کار انجام‌شده و پول موردنیاز تا تکمیل را در یک نمای واحد ندارد.
  • قیمت متریال، اجرت و دستگاه تغییر می‌کند و برآورد اولیه به‌تنهایی برای تصمیم امروز کافی نیست.
  • فاکتورها پراکنده‌اند و ورود دستی آن‌ها زمان‌بر است؛ عکس و ویس باید ورود را سریع کنند، ولی بدون تأیید انسانی نباید روی گزارش اثر بگذارند.
  • بسیاری از پروژه‌های هدف انبار دقیق ندارند؛ بنابراین موجودی انبار نمی‌تواند شرط استفاده از محصول باشد.
  • تیم جدید نباید سورس اصلی را ببیند، اما خروجی باید با شناسه، دسترسی، دیتابیس و UI بامبو قابل ادغام باشد.

۳. اهداف، خروجی‌ها و خارج از محدوده

۳.۱ اهداف MVP

  1. دریافت اقلام و مقادیر متره از خوراک گزارش پیشرفت، Excel یا ورود دستی.
  2. تعریف قیمت واحد اولیه و قیمت روز برای اقلام، با تاریخچه غیرقابل بازنویسی.
  3. محاسبه برآورد اولیه، هزینه واقعی، ارزش روز اجرای واقعی، هزینه باقی‌مانده و پیش‌بینی نهایی.
  4. ثبت فاکتور چندردیفی به روش دستی، عکس و ویس فارسی.
  5. ایجاد Draft از AI، نمایش Confidence و گرفتن تأیید صریح کاربر.
  6. ارائه گزارش مدیریتی و نمودارهای قابل فهم برای رئیس سازمان/مالک.
  7. ساخت ماژول مستقل، قابل تست با Integration Kit و قابل Merge توسط تیم اصلی.

۳.۲ معیار موفقیت محصول

  • مالک بتواند در کمتر از ۳۰ ثانیه پنج عدد اصلی پروژه را ببیند.
  • ثبت یک فاکتور دستی عادی حداکثر در سه مرحله انجام شود.
  • فاکتور عکس/ویس تا قبل از تأیید هیچ اثری بر هزینه واقعی نگذارد.
  • تغییر قیمت روز هیچ فاکتور یا گزارش Snapshot قبلی را تغییر ندهد.
  • هیچ کاربر نتواند داده یا فایل مالی سازمان/پروژه خارج از دامنه خود را ببیند.

۳.۳ خارج از محدوده MVP

خارج از محدودهتوضیح
انبار و موجودیخرید و مصرف جدا ثبت/محاسبه می‌شوند؛ موجودی انبار در این نسخه مدیریت نمی‌شود.
خزانه‌داری و پرداختپرداخت جزئی، حساب بانکی، چک و تسویه خارج از MVP است؛ فاکتور تأییدشده هزینه واقعی محسوب می‌شود.
حسابداری دوبلسند بدهکار/بستانکار، دفتر کل، ترازنامه، مالیات و حقوق در این ماژول نیست.
بازکردن مستقیم MPPفقط ماژول گزارش پیشرفت مسئول خواندن Microsoft Project است.
قیمت خودکار اینترنتیزیرساخت Adapter در نظر گرفته می‌شود ولی Provider قیمت آنلاین در MVP فعال نیست.
فروش/پیش‌فروش واحدماژول فقط داده‌های لازم مانند ارزش روز و هزینه هر مترمربع را فراهم می‌کند.
ساخت سازمان و پروژهماژول مالی از Context موجود میزبان استفاده می‌کند و چنین Endpointهایی نمی‌سازد.

۶.۲ جریان داده

Microsoft Project←کارشناس کنترل پروژه←ماژول گزارش پیشرفت←Snapshot استاندارد←ماژول مالی

ماژول مالی Snapshot را مصرف می‌کند و حق تغییر داده پیشرفت یا بازنویسی فایل MSP را ندارد. هر Snapshot با شناسه و تاریخ گزارش نگه‌داری می‌شود.

۶.۳ Context میزبان

  • organizationId: UUID و روی تمام رکوردهای مالی ذخیره می‌شود.
  • projectId: رشته پایدار و روی تمام رکوردهای مالی ذخیره می‌شود.
  • دامنه مؤثر فقط از Path و Auth Context معتبر می‌آید؛ مقدار Body نادیده گرفته می‌شود.
  • Auth واقعی توسط میزبان انجام می‌شود؛ Mock Header فقط برای توسعه محلی است و ورود آن به Production ممنوع است.
  • تمام مسیرها زیر /api/projects/{projectId}/finance/... و بدون /v1 هستند.

۸. نیازمندی‌های عملکردی

۸.۱ تنظیمات مالی پروژه

FR-001زیربنای کل

برای هر پروژه یک مقدار Decimal مثبت با واحد مترمربع ثبت شود. مقدار اولیه و تمام اصلاح‌ها با تاریخ اثر، دلیل و ثبت‌کننده حفظ شوند.

پذیرش: مقدار صفر/منفی رد شود؛ فقط رئیس سازمان و کارشناس مالی حق تغییر داشته باشند؛ گزارش‌های Snapshot قبلی تغییر نکنند.
FR-002واحد پول و نوع داده

ذخیره‌سازی رسمی تمام مبالغ و قیمت واحد به IRR و عدد صحیح ریال باشد. ستون‌های پولی در PostgreSQL با numeric(18,0) یا نوع Exact معادلِ تأییدشده پیاده شوند؛ در Python از Decimal استفاده شود و در JSON مبلغ به‌صورت رشته عدد صحیح منتقل شود. UI به‌طور پیش‌فرض تومان نمایش دهد و تبدیل فقط در لایه نمایش انجام شود. Import باید IRR/تومان بودن ستون را صریح بخواهد.

پذیرش: ورودی ریالی دارای بخش اعشاری رد شود؛ هیچ تبدیل مبهم یا خودکار براساس حدس عدد انجام نشود.

۸.۲ اقلام مالی و خطوط برآورد

FR-010چهار نوع قلم مالی

سیستم چهار نوع material، labor، equipment و general_cost را پشتیبانی کند. هزینه عمومی می‌تواند مقدار و واحد نداشته باشد.

FR-011شناسه پایدار

هر قلم و خط برآورد شناسه UUID غیرقابل تغییر داشته باشد. عنوان، کد MSP یا نام فعالیت مبنای شناسه نباشند.

FR-012خط مستقل برای Assignment

هر اتصال Activity + Resource یک خط مالی مستقل باشد. تجمیع هم‌نام‌ها فقط از طریق شناسه قلم انجام شود.

FR-013مقدار اولیه و اصلاح‌شده

مقدار اولیه قفل و هر Revision شامل مقدار قبل، مقدار جدید، دلیل، کاربر و زمان باشد.

پذیرش: اصلاح مقدار نباید رکورد اولیه را Update کند.
FR-014منابع ورود

خوراک گزارش پیشرفت، Excel و ورود دستی پشتیبانی شوند و Source هر خط ثبت شود.

۸.۳ خوراک پیشرفت و مقدار مصرف‌شده

FR-020Snapshot نسخه‌دار

ماژول مالی Snapshot شامل شناسه فایل/نسخه، تاریخ گزارش، Taskها و Assignmentها را فقط‌خواندنی مصرف کند.

FR-021ترتیب انتخاب مقدار اجرا
  1. actualQuantity یا Actual Work سازگار با واحد
  2. Assignment Work Complete % × Planned Quantity
  3. Task Progress % × Planned Quantity
  4. Manual Override

Source Method و Quality/Warning در هر خط نمایش داده شود.

FR-022Override دستی

Override فقط با مقدار قبل، مقدار جدید، دلیل غیرخالی، کاربر، زمان و شناسه Snapshot معتبر باشد.

پذیرش: مقدار محاسبه‌شده اصلی قابل مشاهده بماند؛ Override بدون Permission رد شود.
FR-023عبور از مقدار برآورد

ثبت مقدار بیشتر از برآورد مسدود نشود؛ هشدار، مقدار و درصد انحراف نمایش داده شود و دلیل اجباری در Audit ثبت شود.

۸.۴ قیمت و تاریخچه قیمت

FR-030قیمت پایه و Override پروژه

قیمت پایه در سطح سازمان و قیمت Override در سطح پروژه تعریف شود؛ هنگام محاسبه، Override معتبر پروژه مقدم است.

FR-031تاریخچه Strict Append-only

هر تغییر قیمت فقط با INSERT یک PriceVersion جدید و effectiveFrom انجام شود. هیچ رکورد قیمت تاریخی - حتی برای بستن effectiveTo - UPDATE نمی‌شود. قیمت معتبر در تاریخ گزارش از آخرین نسخه واجد effectiveFrom ≤ asOf با ترتیب نسخه/ثبت قطعی انتخاب می‌شود و Snapshot گزارش شناسه همان نسخه را Pin می‌کند.

پذیرش: ایجاد قیمت جدید، بایت/مقادیر رکوردهای PriceVersion قبلی را تغییر ندهد.
FR-032ورود گروهی قیمت

قالب Excel شامل کد قلم، قیمت، واحد پول، تاریخ اثر و Scope باشد. پیش‌نمایش خطاها قبل از Commit اجباری است.

۸.۵ واحد و تبدیل واحد

FR-040واحد پایه

هر قلم مقداری یک واحد پایه و بُعد مشخص داشته باشد. مقادیر با ابعاد متفاوت جمع نشوند.

FR-041تبدیل قابل تنظیم

تبدیل‌های سازمانی و Override پروژه با ضریب Decimal، تاریخ اثر و Audit پشتیبانی شوند؛ مانند تن به کیلوگرم یا روز دستگاه به ساعت.

پذیرش: تبدیل بدون ضریب معتبر یا بین ابعاد ناسازگار رد شود.

۸.۶ فاکتور دستی و چندردیفی

FR-050سربرگ فاکتور

شماره فاکتور، تاریخ، فروشنده/ارائه‌دهنده، توضیح، تخفیف، مالیات، حمل، سایر هزینه‌ها، مبلغ نهایی، Source و Status ثبت شود.

FR-051خطوط فاکتور

هر خط به خط برآورد یا هزینه عمومی متصل شود و مقدار، واحد، قیمت واحد، مبلغ خط و توضیح داشته باشد.

FR-052توزیع تعدیلات سربرگ

برای گزارش ریز اقلام، تخفیف/مالیات/حمل/سایر هزینه‌ها به نسبت مبلغ خام خطوط توزیع شوند؛ کاربر می‌تواند یک هزینه را مستقیماً به قلم «هزینه عمومی» تخصیص دهد. اختلاف گردکردن به‌صورت قطعی به آخرین خط تخصیص می‌یابد.

FR-053تشخیص تکراری

Idempotency Key، هش فایل یکسان و تأیید دوباره Draft تکرار قطعی‌اند و مسدود می‌شوند. شباهت فروشنده+شماره+تاریخ+مبلغ هشدار می‌دهد و ادامه فقط با دلیل مجاز است.

۸.۷ عکس، ویس و AI

FR-060آپلود امن

حد محصول در MVP قطعی است: تصویر JPEG/PNG/WebP حداکثر ۱۰ MiB و صوت MP3/M4A/WAV/OGG حداکثر ۲۵ MiB. Extension، MIME و Magic Bytes بررسی و نام ذخیره تصادفی شود؛ SVG ممنوع است. سازگاری Edge/Web Server میزبان با همین حدود، Gate فنی پیش از Merge است و تصمیم محصولی باز محسوب نمی‌شود.

FR-061Provider-neutral Extraction

دو Interface مستقل برای Image و Voice وجود داشته باشد. Provider و Credential در محیط اجرا تزریق و در Source ثبت نشوند.

FR-062Draft و Confidence

هر فیلد مقدار استخراج‌شده، Confidence، مقدار تأییدشده و علامت ویرایش کاربر داشته باشد. فاکتور چندردیفی از عکس پشتیبانی شود و ویس فارسی بتواند Draft چندخطی بسازد.

FR-063تأیید انسانی

همان ارسال‌کننده، پس از مشاهده فایل و Draft، می‌تواند آن را اصلاح و تأیید کند. قبل از تأیید، اثر مالی دقیقاً صفر است.

FR-064انتخاب Provider

تیم تا پایان روز دوم، دو گزینه واقعی OCR/Voice فارسی را با نمونه خروجی، هزینه، محدودیت داده، Latency و کیفیت پیشنهاد می‌دهد؛ شروع اتصال Production-like فقط بعد از تأیید کتبی بامبو است.

۸.۸ چرخه عمر فاکتور

FR-070سه چرخه وضعیت مستقل

سه State Machine مستقل وجود دارد: File Processing با uploaded → processing → ready و مسیر خطای failed؛ Extraction Review با awaitingReview → accepted/rejected؛ و Invoice با draft → awaitingConfirmation → confirmed و سپس voided/corrected از طریق سند مرتبط. یک فیلد Status مشترک بین فایل، استخراج و فاکتور ممنوع است.

پذیرش: تغییر وضعیت فایل یا Extraction به‌تنهایی هیچ اثر مالی ایجاد نکند؛ فقط Invoice confirmed وارد هزینه واقعی شود.
FR-071غیرقابل تغییر بودن

فاکتور Confirmed با PATCH/DELETE قابل تغییر نیست. اصلاح فقط با Void/Reversal/Corrective Invoice و رابطه صریح با سند اصلی انجام می‌شود.

FR-072هزینه واقعی

هر فاکتور Confirmed، مستقل از پرداخت، در هزینه واقعی لحاظ می‌شود. فاکتور Void یا Reversal براساس اثر علامت‌دار در محاسبات اعمال می‌شود.

۸.۹ هزینه عمومی

FR-080قاعده هزینه عمومی

برآورد اولیه و اصلاح‌شده مبلغی هستند. هزینه واقعی از فاکتورهای تأییدشده به دست می‌آید. باقی‌مانده برابر حداکثرِ «برآورد اصلاح‌شده منهای هزینه واقعی، صفر» و پیش‌بینی نهایی برابر «هزینه واقعی + باقی‌مانده» است. اگر هزینه واقعی بیشتر شود، وضعیت «بیشتر از برآورد» نمایش داده می‌شود.

۸.۱۰ داشبورد و گزارش

FR-090کارت‌های اصلی

برآورد اولیه، هزینه واقعی، ارزش روز کار انجام‌شده، هزینه باقی‌مانده فیزیکی، پول موردنیاز برای ادامه، پیش‌بینی نهایی، هزینه واقعی هر مترمربع و پیش‌بینی هر مترمربع.

FR-091نمودارها

  • تفکیک متریال، نیروی انسانی، دستگاه و هزینه عمومی
  • بیشترین انحراف قیمت
  • بیشترین انحراف مقدار
  • ارزش روز انجام‌شده و هزینه باقی‌مانده
FR-092گزارش Snapshot

صدور گزارش نسخه‌های Snapshot پیشرفت، مقدارها، قیمت‌ها، تبدیل‌ها، مجموعه فاکتورها، زیربنا و تمام شاخص‌ها را Pin می‌کند. گزارش بعداً با داده جدید تغییر نمی‌کند.

FR-093خروجی

HTML چاپی A4، چاپ PDF مرورگر و CSV UTF-8 با BOM ارائه شود. PDF Server-side و XLSX در MVP اجباری نیست.

۸.۱۱ Audit و حذف

FR-100رویدادهای ممیزی

تغییر قیمت، Revision مقدار، Override پیشرفت، تأیید/ابطال/اصلاح فاکتور، نادیده‌گرفتن هشدار تکراری، دسترسی به پیوست و صدور گزارش ثبت شوند.

FR-101حذف و Retention

تاریخچه مالی Confirmed و Report Snapshot صادرشده حذف یا بازنویسی خودکار نمی‌شوند. Draft ردشده/رهاشده بعد از ۹۰ روز قابل پاک‌سازی کنترل‌شده است و پیوست فاکتور تأییدشده خودکار حذف نمی‌شود. مدت Retention حقوقی/سازمانی Report Snapshot هنوز تعیین نشده؛ تا تصویب سیاست جداگانه، هیچ Job زمان‌دار مجاز به حذف Snapshot صادرشده نیست.

قواعد دیتابیس

  • هر جدول مالی دارای organization_id uuid و project_id text است.
  • شناسه موجودیت‌های مالی UUID تولیدشده و مستقل از عنوان است.
  • Money و Unit Price با numeric(18,0) و Python Decimal؛ Quantity/Conversion با numeric(18,4) یا دقت بیشترِ تأییدشده؛ Timestamp با timestamptz UTC.
  • Status با Text + CHECK و بدون PostgreSQL ENUM.
  • هیچ FK از پروژه/سازمان به تاریخچه مالی ON DELETE CASCADE ندارد.
  • هر Query علاوه بر ID رکورد با هر دو Scope محدود می‌شود.
  • SQL نهایی باید روی PostgreSQL 16 و 18 دو بار متوالی بدون خطا اجرا شود.

۱۳. نیازمندی‌های غیرعملکردی و امنیت

۱۳.۱ امنیت و Multi-tenancy

  • هیچ Endpoint، Query یا فایل بدون Scope دوگانه سازمان و پروژه پذیرفته نمی‌شود.
  • عضو پروژه بدون Permission مالی نباید فایل یا داده مالی را ببیند.
  • فایل‌ها از مسیر Static عمومی سرو نمی‌شوند؛ دسترسی از Endpoint اختصاصی و Audit‌شده است.
  • مقدار Scope در Body نادیده گرفته می‌شود.
  • عملیات حساس با Idempotency، Transaction و Version Check انجام می‌شوند.
  • پیش از Merge، تصمیم CSRF/Origin validation و Security Headers توسط تیم اصلی بسته و تست می‌شود.

۱۳.۲ فایل

  • Allowlist پسوند، MIME و Magic Bytes، نام تصادفی و Hash اجباری است؛ سقف قطعی محصول ۱۰ MiB تصویر و ۲۵ MiB صوت است و Edge میزبان باید پیش از Merge با این سقف‌ها Verify شود.
  • فایل اجرایی، HTML و SVG رد می‌شود.
  • راهکار Malware Scanning پیش از Production باید توسط تیم اصلی تعیین شود؛ نبود آن مانع Go-live است.

۱۳.۳ AI

  • Provider باید Server-side باشد و Browser مستقیماً به سرویس خارجی وصل نشود.
  • در خطا/قطعی Provider، فایل حفظ و ورود دستی همیشه ممکن باشد.
  • Confidence پایین با هشدار و Highlight نشان داده شود؛ هیچ Auto-confirm وجود ندارد.
  • در قرارداد Provider، سیاست استفاده از داده، Retention و آموزش مدل بررسی شود.

۱۳.۴ کارایی و مقیاس

  • Pagination پیش‌فرض ۵۰ و سقف ۲۰۰ رکورد.
  • Dashboard برای پروژه نمونه با ۵۰هزار خط فاکتور در Staging حداکثر در ۳ ثانیه در صدک ۹۵ پاسخ دهد.
  • APIهای فهرست در صدک ۹۵ حداکثر ۲ ثانیه و Export سنگین به‌صورت Job/Status در صورت عبور از محدودیت Sync.
  • تمام Queryهای پرتکرار Index ترکیبی با Scope داشته باشند.

۱۳.۵ سازگاری و وابستگی

  • بدون Dependency جدید مگر با درخواست کتبی، دلیل و جایگزین‌ها.
  • بدون Docker/Redis/Celery/S3 و بدون درخواست خارجی مرورگر.
  • تست SQL روی PostgreSQL 16 و 18 اجباری است.
  • فرانت بدون Build Step و با ES Modules تحویل می‌شود.

۱۶.۲ Definition of Done

Done یعنی: ماژول مقابل Mock Host اجرا شود؛ تمام Contract و Acceptance Testها Pass شوند؛ هیچ وابستگی به Mock Auth در کد Production-like نباشد؛ هیچ Query بدون Scope، پول Float، Parse مستقیم MPP، فایل عمومی، Invoice Confirmed قابل ویرایش یا Report Snapshot قابل تغییر وجود نداشته باشد.

۱۶.۳ شرایط رد تحویل

  • ظاهر کامل ولی محاسبات یا Scope نادرست.
  • کد تولیدشده با AI که توسعه‌دهنده نتواند توضیح دهد.
  • Hard-code سازمان/پروژه، Secret، Provider Key یا مسیر سیستم.
  • کپی Mock Header به پیاده‌سازی نهایی.
  • استفاده از Float برای مبلغ، تغییر تاریخچه یا حذف آبشاری مالی.
  • اضافه‌کردن Framework/Library خارج از قرارداد بدون تأیید.
  • نداشتن تست منفی برای دسترسی سازمان/پروژه و فایل.
