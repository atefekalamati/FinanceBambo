# میزبان توسعه ماژول مالی

این پوشه **فقط برای توسعه** است و هرگز نباید Deploy شود.

ماژول مالی عمداً Composition Root ندارد: طبق [INTEGRATION_GUIDE_FA.md](../INTEGRATION_GUIDE_FA.md)
میزبان BAMBO باید Connection دیتابیس، ۱۱ Service و ۶ Port را در `application.state` بگذارد.
تا وقتی آن میزبان در دسترس نباشد، هیچ راهی برای اجرای واقعی ماژول وجود ندارد و Frontend
ناچار روی Adapterهای Mock می‌ماند. این پوشه همان نقش را برای محیط محلی بازی می‌کند.

## اجرا

```bash
# ۱. دیتابیس
docker compose -f ../../docker-compose.dev.yml up -d

# ۲. میزبان (از پوشه backend)
python -m devhost
```

سپس <http://127.0.0.1:8000> را باز کنید.

گزینه‌ها:

| گزینه | کار |
|---|---|
| `--reseed` | پروژه نمونه را پاک و دوباره بارگذاری می‌کند |
| `--port` | پورت، پیش‌فرض `8000` |
| `--dsn` | رشته اتصال، یا متغیر محیطی `FINANCE_DEV_DSN` |

Migrationها در هر بار بالا آمدن اجرا می‌شوند و چون همگی `IF NOT EXISTS` هستند، تکرارشدنی‌اند.
Seed فقط وقتی اجرا می‌شود که پروژه نمونه وجود نداشته باشد، مگر با `--reseed`.

## چرا Frontend از حالت Mock خارج می‌شود

دو شرط باید هم‌زمان برقرار باشد:

1. **Context میزبان** — `bootstrap.js` با `getHostContext()` تصمیم می‌گیرد و آن هم
   `window.__BAMBO_FINANCE_CONTEXT__` را می‌خواند. این میزبان `index.html` را با آن شیء
   تزریق‌شده **پیش از** تگ `<script type="module">` سرو می‌کند.
2. **هم‌ریشه بودن** — `api-client.js` تابع `assertSameOrigin` دارد و درخواست به Origin دیگر
   را رد می‌کند. پس API و فایل‌های استاتیک باید از یک پروسه و یک پورت سرو شوند؛ همین کار
   اینجا انجام می‌شود.

## آنچه واقعی است و آنچه ساختگی

| بخش | وضعیت |
|---|---|
| Schema و داده | واقعی: PostgreSQL 16، همان Migrationهای تولید |
| محاسبات مالی | واقعی: همان Domain و Repositoryهای تولید |
| احراز هویت | **ساختگی**: یک کاربر ثابت با هر پنج مجوز مالی |
| عضویت سازمان و پروژه | **ساختگی**: فقط Tenant نمونه پذیرفته می‌شود |
| خوراک پیشرفت | **ساختگی**: Assignmentهای ثابت از `seed.py` |
| فهرست فعالیت‌ها | **ساختگی**: در حافظه |
| ذخیره فایل | محلی، زیر `devhost/.files` |
| استخراج AI | **غیرفعال**: عمداً خطا می‌دهد تا داده فاکتور جعل نشود |

## داده‌ها کجا ذخیره می‌شوند

| لایه | محل | محتوا |
|---|---|---|
| **Schema** | `backend/migrations/*.sql` | فقط ساختار: جدول، Constraint، Trigger. هیچ داده‌ای ندارد و دست‌نخورده می‌ماند. |
| **داده Seed** | `backend/devhost/seed.sql` | SQL خام و قابل ویرایش. با `python -m devhost.generate_seed_sql` از روی قواعد Mock بازتولید می‌شود. |
| **داده زنده** | Volume داکر `finance_finance-dev-data` | هرچه در UI ثبت کنید اینجا می‌نشیند و با Restart باقی می‌ماند. |
| **خوراک میزبان** | `backend/devhost/seed.py` | آنچه Port میزبان *سرو* می‌کند نه *ذخیره*: خوراک پیشرفت و فهرست فعالیت‌ها. |

پاک‌کردن کامل داده زنده: `docker compose -f ../../docker-compose.dev.yml down -v`

## داده نمونه

یک پروژه ساختمانی با زیربنای ۱۴٬۲۵۰ مترمربع که هر مسیر محاسباتی را فعال می‌کند:

- **قیمت‌های تغییرکرده** پس از تصویب برآورد، در دو Scope سازمان و پروژه
- **جرثقیل بدون قیمت روز** تا مسیر «محاسبه ناقص» دیده شود، نه اینکه فرضی بماند
- **اضافه‌برداشت مقدار** در دیوارچینی → هشدار `QUANTITY_OVERRUN`
- **اضافه‌خرج هزینه عمومی** در عوارض شهرداری → هشدار `GENERAL_COST_OVERRUN`
- **خط بدون مقدار واقعی** تا Fallback درصد پیشرفت فعال شود
- فاکتورها در وضعیت‌های `confirmed`، `awaitingConfirmation` و `draft`

## هشدار

`ports.py` هویت را جعل می‌کند و همه مجوزها را می‌دهد. تنها اتصال بین این پوشه و
`backend/app` جهت وارد کردن است: `devhost` از `app` استفاده می‌کند، ولی `app` هرگز
از `devhost` چیزی وارد نمی‌کند. کد تولید از وجود این پوشه بی‌خبر است.
