# مالکیت داده: Core در برابر Finance

این سند می‌گوید هر داده‌ای که Finance با آن کار می‌کند **از کجا می‌آید** و **چه کسی مالکش
است**. سؤالی که به آن پاسخ می‌دهد ساده است و پاسخ اشتباهش گران: وقتی داده نمونه در Production
ممنوع باشد، هر ردیف واقعاً از کجا می‌آید؟

---

## قاعده بنیادی

> **Production هرگز داده نمونه/Demo/Seed دریافت نمی‌کند.** داده Mock و Seed فقط برای
> DEV/TEST است، بدون استثنا.

در Production داده Finance دقیقاً دو منشأ دارد:

| منشأ | چه چیزی | چگونه |
|---|---|---|
| **Core** | سازمان، پروژه، کاربر، عضویت، نسخه فایل MSP، Snapshot، Task، فایل/مدیا، مجوزها | از طریق Adapterهای تأییدشده خوانده می‌شود؛ Finance هرگز این رکوردها را نمی‌سازد و مالکشان نیست |
| **Finance** | تنظیمات، اقلام، برآورد، Revision، قیمت، تبدیل واحد، اصلاح پیشرفت، فاکتور، فایل پیوست، استخراج، گزارش، ورود گروهی، ممیزی | از طریق API خود ماژول Finance وارد یا تولید می‌شود |

Finance علاوه بر این، **ارجاع** به شناسه‌های Core و **حقایق تثبیت‌شده** لازم برای بازتولید
محاسبات را ذخیره می‌کند. اما مجموعه داده کامل Core را کپی نمی‌کند.

---

## طبقه‌بندی

| رده | یعنی | نمونه |
|---|---|---|
| **CORE_SOURCE** | Core مالک و تولیدکننده است؛ Finance زنده می‌خواند و رکورد کامل را ذخیره نمی‌کند | Snapshot و Task در MSP، عضویت، مجوزها |
| **CORE_REFERENCE** | شناسه‌ای از Core که Finance نگه می‌دارد تا به یک حقیقت Core اشاره کند | `organization_id`، `project_id`، شناسه کاربر، `host_snapshot_id` |
| **FINANCE_SOURCE** | از طریق Finance وارد یا تولید شده؛ Finance مالک رکورد است | قیمت، برآورد، فاکتور تأییدشده |
| **FINANCE_DERIVED** | Finance در لحظه خواندن محاسبه می‌کند؛ ذخیره نمی‌شود | ارزش اجراشده، هزینه باقی‌مانده، پیش‌بینی نهایی |
| **FINANCE_SNAPSHOT** | یک‌بار محاسبه و برای بازتولیدپذیری منجمد می‌شود | `report_snapshots.snapshot_payload`، `unit_price_snapshot_irr` |
| **DEV_TEST_ONLY** | فقط برای شبیه‌سازی محلی؛ هرگز نباید به Production برسد | `devhost/seed.py`، `frontend/src/adapters/mock/*` |

## چرخه عمر مرجع Snapshot پیشرفت

**مشکلی که وجود داشت:** تا Revision 0006، تنها چیزی که در `progress_snapshot_refs`
می‌نوشت Seed توسعه بود. روی یک دیتابیس واقعی این جدول همیشه خالی می‌ماند، هر گزارش زنده
۴۰۴ می‌گرفت، و هیچ گزارشی هرگز صادر نمی‌شد. نیمه گزارش‌گیری ماژول عملاً غیرقابل استفاده بود.

**حالا چه اتفاقی می‌افتد:**

1. Core یک Snapshot منتشر می‌کند (`msp_snapshots.id` از نوع `bigint`).
2. عملیاتی در Finance که باید بازتولیدپذیر بماند — **صدور گزارش** یا **ثبت اصلاح دستی** — از
   Adapter می‌پرسد Snapshot جاری این پروژه کدام است.
3. Finance یک مرجع تغییرناپذیر می‌سازد، یا اگر قبلاً برای همان Snapshot ساخته شده، **همان را
   دوباره استفاده می‌کند**.
4. محاسبه با آن مرجع ادامه می‌یابد و شناسه‌اش در گزارش صادرشده Pin می‌شود.

### خواندن هرگز نمی‌نویسد

`GET /reports/live` و `GET /overview` **هیچ مرجعی نمی‌سازند**. باز کردن یا Refresh کردن یک
صفحه رویداد مالی نیست، و `/overview` فقط با `finance.view` محافظت می‌شود — مجوز خواندنی که
بی‌صدا `INSERT` کند، مجوزی است که معنایش با کارش فرق دارد.

| عملیات | مرجع می‌سازد؟ |
|---|---|
| `GET /reports/live` | ❌ فقط می‌خواند و محاسبه می‌کند |
| `GET /overview` | ❌ |
| `POST /report-snapshots` (صدور گزارش) | ✅ Pin می‌کند، چون گزارش صادرشده تغییرناپذیر و باید بازتولیدپذیر باشد |
| `POST /estimate-lines/{id}/progress-override` | ✅ Pin می‌کند |

**معنای `progressSnapshotId` در پاسخ گزارش زنده:**

- اگر مرجعی برای آن Snapshot Core وجود داشته باشد → همان UUID پایدار Finance برگردانده می‌شود.
- اگر وجود نداشته باشد → **`null`**. هنوز شناسه‌ای در Finance ساخته نشده، و ساختن یک UUID تازه
  در هر درخواست یعنی دادن شناسه‌ای به Client که با هر Refresh عوض می‌شود و به هیچ‌چیز اشاره
  نمی‌کند.
- در هر دو حالت `hostSnapshotId` می‌گوید محاسبه از کدام Snapshot Core انجام شده.

> **این دو هرگز جای هم استفاده نمی‌شوند.** `progressSnapshotId` یک UUID متعلق به Finance است و
> `hostSnapshotId` یک `bigint` متعلق به Core. جایگزینی یکی با دیگری همان اشتباه هویتی است که
> کل این طراحی برای حذفش وجود دارد.

**نبودِ مرجع یعنی صفر Override، نه صفر پیشرفت.** Feed مثل همیشه خوانده و محاسبه می‌شود؛ خطی که
Feed نتواند پاسخش را بدهد با هشدار خودش «نامعلوم» می‌ماند، نه اینکه صفرِ اندازه‌گیری‌شده شود.

**هیچ عملیات دستی از سمت کاربر لازم نیست.** کسی نباید شناسه Core را دستی رونویسی کند.

**چه چیزی مال کیست:**

| ستون | مالک | توضیح |
|---|---|---|
| `id` | Finance | کلید اصلی ردیف |
| `progress_snapshot_id` | Finance | شناسه عمومی؛ همان که در URL و در Payload گزارش صادرشده دیده می‌شود |
| `host_snapshot_id` | **Core** | `msp_snapshots.id` — `bigint` |
| `host_file_version_id` | **Core** | `msp_file_versions.id` — `bigint` |

هنگام درخواست Feed از میزبان، Finance با **شناسه میزبان** سؤال می‌کند، نه با UUID خودش؛
میزبان UUID فایننس را نمی‌شناسد.

**بدون FK فیزیکی.** Core با حذف پروژه، Snapshotها را CASCADE می‌کند. یک کلید `RESTRICT`
حذف پروژه را در Core مسدود می‌کرد و یک کلید `CASCADE` تاریخچه مالی را از بین می‌برد. هیچ‌کدام
قابل قبول نیست، پس اعتبارسنجی در مرز Adapter انجام می‌شود.

**Idempotency:** Index یکتای جزئی روی `(organization_id, project_id, host_snapshot_id)`
تضمین می‌کند یک Snapshot از Core هرگز دو مرجع Finance نسازد — حتی اگر دو درخواست هم‌زمان
برسند.

## راه‌اندازی یک پروژه واقعی جدید

یک پروژه تازه هیچ داده Finance ندارد، و **این با Seed حل نمی‌شود**. موارد زیر باید از طریق
API خود Finance ساخته شوند:

| قدم | مسیر | اگر نباشد چه می‌شود |
|---|---|---|
| تنظیمات مالی (زیربنا، ارز) | `PATCH /settings` | شاخص‌های هر مترمربع `null` می‌شوند و هشدار `GROSS_AREA_MISSING` صادر می‌شود |
| تبدیل واحد لازم | `POST /unit-conversions` | خرید با واحدی غیر از واحد پایه از محاسبه کنار می‌رود، با هشدار `UNIT_CONVERSION_MISSING` |
| اقلام مالی | `POST /resources` یا ورود اکسل | برآوردی وجود نخواهد داشت |
| خطوط برآورد | `POST /estimate-lines` یا ورود اکسل | گزارش خالی است |
| قیمت روز | `POST /resources/{id}/prices` یا ورود اکسل | ارزش اجراشده `null` می‌شود، با هشدار `CURRENT_PRICE_MISSING` |

> **مقدار پیش‌فرض ساختگی برای خاموش‌کردن هشدارها ساخته نمی‌شود.** هر ورودی غایب به `null` و
> یک هشدار نام‌دار تبدیل می‌شود، نه به صفر. گزارشِ صادقانه ناقص از گزارشِ با اطمینانِ غلط
> بهتر است. این همان قاعده «`missing` مساوی `zero` نیست» است.

## داده نمونه: کجا زندگی می‌کند و چرا نمی‌تواند فرار کند

| مکان | محتوا |
|---|---|
| `backend/devhost/` | `seed.py`، `seed.sql`، Providerهای Seed شده، `synthetic_progress.py` |
| `frontend/src/adapters/mock/` | Mockهای مرورگر |

**مهار ساختاری است، نه قراردادی:** کتابخانه Finance هیچ‌کدام از این دو را import نمی‌کند.
`synthetic_progress.py` علاوه بر آن `assert_development_only()` را صدا می‌زند.

Seed **Fail-closed** است و دو شرط می‌خواهد: `APP_ENV` یکی از `development`/`dev`/`test` باشد،
**و** `FINANCE_ALLOW_SEED=true` صریحاً تنظیم شده باشد. `staging` قابل Seed نیست.

**راه‌اندازی Host هیچ Migrationی اجرا نمی‌کند.** Alembic تنها مکانیزم Schema است ولی صریح
اجرا می‌شود (`cd backend && alembic upgrade head`). اگر Schema نباشد، Host با پیام روشن
متوقف می‌شود و آن را نمی‌سازد.

**Revisionهای Alembic هرگز داده کسب‌وکار بارگذاری نمی‌کنند.** تنها داده‌ای که یک Revision
اجازه نوشتن دارد، Backfill ستونی است که خودش همان لحظه اضافه کرده — همان کاری که `0004`
می‌کند.

## وضعیت دیتابیس اصلی BAMBO

در این مرحله **هیچ تغییری روی دیتابیس اصلی انجام نشده است**. هیچ اتصالی، هیچ Migrationی،
هیچ `stamp`ی. تمام کار در Repository خود Finance انجام شده و اجرای Migration روی دیتابیس
محلی هم هنوز انجام نشده است.
