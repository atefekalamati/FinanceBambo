# هم‌راستایی داده نمایشی — فرانت‌اند، بک‌اند، دیتابیس

این سند نشان می‌دهد یک پروژه نمایشی در هر سه لایه **یک عدد** را نشان می‌دهد، و هر جا که
تفاوتی هست، دلیلش نوشته شده.

## چرا این هم‌راستایی خودبه‌خود حفظ می‌شود

مقادیر در سه جا کپی نشده‌اند؛ از یک تعریف مشتق می‌شوند:

```
frontend/src/adapters/mock/*.js      ← تعریف اصلی سناریوی نمایشی
        ↓ (به‌صورت دستی آینه شده، طبق مستند خودِ فایل)
backend/devhost/seed.py              ← ثابت‌های پایتون
        ↓ generate_seed_sql.py
backend/devhost/seed.sql             ← ردیف‌های جدول‌های مالی
        ↓ scripts/demo/seed_core_mirror.py  (همان ثابت‌ها را import می‌کند)
جدول‌های Mirror هسته در دیتابیس دمو
```

نکته مهم: `seed_core_mirror.py` مقادیر را **تایپ نمی‌کند**، بلکه `devhost.seed` را import
می‌کند. پس Mirror هسته نمی‌تواند با داده مالی ناهماهنگ شود — حتی اگر کسی یادش برود
به‌روزرسانی کند.

## تفاوت‌هایی که عمدی‌اند — با دلیل

| مورد | فرانت‌اند | بک‌اند / دیتابیس | چرا متفاوت است |
|---|---|---|---|
| تاریخ اثر تنظیمات | `2026-08-06` | `2026-06-01` | تاریخ Mock **بعد از** جدیدترین Snapshot خودش است. Mock چیزی از آن محاسبه نمی‌کند، ولی گزارش واقعی زیربنا را با شرط `effective_from <= تاریخ گزارش` پیدا می‌کند — با تاریخ Mock، **همه سنجه‌های هر مترمربع بی‌پاسخ می‌شدند**. مقدار و دلیل یکی است؛ فقط تاریخ عقب کشیده شده تا واقعاً اعمال شود |
| شناسه‌های حالت Standalone | `finance_frontend_demo` / سازمان `…000002` | `sample_site_01` / سازمان `11111111-…` | حالت Standalone یک مستأجر خیالی جداست برای توسعه UI بدون بک‌اند. **دموی فردا در حالت میزبان اجرا می‌شود** و شناسه‌های واقعی دمو را می‌بیند |
| `finance_report.issue` در Standalone | در فهرست مجوزها **هست** | در هسته **نیست** | حالت Standalone کل مسیر UI را تمرین می‌کند، از جمله دکمه صدور. عمداً دست‌نخورده ماند تا توسعه فرانت‌اند مختل نشود. **در حالت میزبان این مجوز به مرورگر داده نمی‌شود** و دکمه اصلاً ظاهر نمی‌شود |
| شکل شناسه فاکتورها | شمارنده عددی | UUID قطعی | جدول به UUID نیاز دارد؛ قاعده تولید یکی است |

**هیچ تفاوت بی‌توضیحی در مقادیر حیاتی دمو باقی نمانده است.**

## اصلاحی که در همین بررسی انجام شد

پیش از این، صفحه میزبان فهرست مجوزها را **ثابت** به مرورگر تزریق می‌کرد — شامل
`finance_report.issue`.

> **نتیجه‌اش این می‌شد:** مرورگر دکمه «صدور گزارش رسمی» را نشان می‌داد، کاربر کلیک می‌کرد،
> و API با ۴۰۳ رد می‌کرد. یعنی رابط کاربری چیزی را وعده می‌داد که سرور از قبل رد کرده بود —
> بدترین ترکیب ممکن.

حالا صفحه میزبان همان `AuthContext`ی را می‌خواند که API روی آن تصمیم می‌گیرد. در حالت
اتصال به هسته، مرورگر دقیقاً این چهار مجوز را می‌بیند:

```
finance.edit · finance.view · finance_report.export · finance_report.view
```

و دکمه صدور **اصلاً ساخته نمی‌شود**. رابط کاربری و سرور یک حرف می‌زنند.
