# ممیزی قیمت‌گذاری تجهیزات — پیش از پیاده‌سازی

> Mission C، فاز ۱. این سند **ممیزی** است، نه طرح پیاده‌سازی. هیچ کدی در جریان آن تغییر
> نکرد و هیچ چیزی روی دیتابیس نوشته نشد.

| | |
|---|---|
| دیتابیس | `bambo_canonical_test` |
| پروژه | `terrace` |
| نسخهٔ مهاجرت | `0036` |
| تاریخ ممیزی | ۱ مهر ۱۴۰۵ (2026-09-22) |

همهٔ اعداد این سند از همان دیتابیس خوانده شده‌اند. هر جا عددی نیامده، یعنی سنجیده نشده —
نه اینکه صفر است.

---

## خلاصهٔ یک‌خطی

زیرساخت قیمت‌گذاری دستی از قبل کامل است و کار می‌کند؛ تجهیزات فقط هرگز وارد آن نشده‌اند.
شکاف واقعی از چیزی که بریف فرض کرده کوچک‌تر است، ولی سه تصمیم دارد که کد نمی‌تواند به‌جای
آدم بگیرد.

---

## ۱. معماری فعلی

دو مسیر قیمت‌گذاری جدا وجود دارد و هرگز به هم نمی‌رسند:

```
مسیر مصالح:  provider_items → price_observations → finance_item_price_mappings
مسیر منابع:  finance_resources → price_versions → estimate_lines → rollup
```

ستون‌های `price_versions`:

```
resource_id, scope_kind, version, unit_price_irr, effective_from,
reason, created_by, created_at
```

یعنی نسخه‌دار، تاریخ‌دار، با هویت کاربر و دلیل اختیاری. هر چیزی که فاز ۲ از یک «سیستم
قیمت‌گذاری دستی» می‌خواهد، همین‌جاست. ساختن جدول تازه برای تجهیزات، بازسازیِ چیزی است که
قبلاً ساخته شده.

---

## ۲. تجهیزات الان کجاست

`resource_type='equipment'` از قبل در CHECK جدول `finance_resources` هست:

```sql
CHECK (resource_type = ANY (ARRAY['material', 'labor', 'equipment', 'general_cost']))
```

در `terrace` نوزده تجهیز وجود دارد:

| واحد پایه | تعداد منبع | خط برآورد | قیمت‌دار |
|---|---:|---:|---:|
| `hour` | 18 | 426 | **0** |
| `day` | 1 (جرثقیل) | **0** | 1 |

هویتِ «نام + واحد» که فاز ۲ می‌خواهد، از همین حالا برقرار است: `title` به‌علاوهٔ `base_unit`.
جرثقیل با واحد `day` و جرثقیل ۱۰ تن با واحد `hour` دو سطر جدا هستند و باید هم باشند.

**نکتهٔ کلیدی:** دو نیمهٔ کار هرگز به هم نرسیده‌اند. جرثقیل قیمت دارد ولی خط برآورد ندارد؛
هجده تجهیز ساعتی خط برآورد دارند ولی نه مقدار دارند نه قیمت. هیچ‌کدام هزینه تولید نمی‌کنند،
به دو دلیل متفاوت.

---

## ۳. چرا باید از همین جدول‌ها استفاده شود

چون با مصالح کار می‌کند. همان زنجیره، همان جدول‌ها:

```
material :  409 خط  ·  120 مقدار مستقیم + 289 از completions = ۱۰۰٪  ·  120 قیمت‌دار   ✓
equipment:  426 خط  ·    0 مقدار مستقیم +   0 از completions =   ۰٪  ·    0 قیمت‌دار   ✗
```

پوشش مقدار با همان عبارتی سنجیده شد که خود کد استفاده می‌کند
(`EFFECTIVE_ORIGINAL_QUANTITY` در `domain/estimate_basis.py`)، نه فقط با
`original_quantity`. تجهیزات از **هیچ** منبعی مقدار ندارند: نه ستون خودشان، نه جدول
completions، نه بازنگری.

### سلسله‌مراتب قیمت از قبل پیاده شده است

در `repositories/reports.py`:

```sql
ORDER BY (pv.scope_kind='project') DESC, pv.effective_from DESC,
         pv.version DESC, pv.created_at DESC, pv.id DESC
```

یعنی پروژه بر سازمان مقدم است و تاریخ اثر هم رعایت می‌شود. توزیع واقعی:

```
project      122 سطر
organization   3 سطر
```

### مکانیزم بازنگری مقدار هم از قبل هست

`estimate_revisions` دقیقاً این‌ها را نگه می‌دارد:

```
previous_quantity, new_quantity, reason, created_by, created_at, revision
```

که تمامِ خواستهٔ فاز ۶ است — مقدار قبلی، مقدار جدید، کاربر، زمان، دلیل اختیاری، نسخه‌بندی.
اولویتِ دستی بر محاسبه‌شده هم نوشته شده، در `repositories/resources.py`:

```sql
COALESCE((SELECT r.new_quantity FROM estimate_revisions r
           WHERE ... ORDER BY r.revision DESC LIMIT 1),
         effective_original_quantity)
```

این جدول **صفر سطر** دارد. ساخته شده و هرگز استفاده نشده.

## ۴. شکاف واقعی

| فاز | وضعیت |
|---|---|
| ۲ — قیمت‌گذاری تجهیزات | زیرساخت آماده؛ تجهیزات واردش نشده‌اند |
| ۳ — API صفحهٔ تنظیمات | باید ساخته شود |
| ۴ — محاسبهٔ مقدار | باید ساخته شود |
| ۵ — `quantitySource` | **مهاجرت لازم ندارد**؛ از `current_revision > 0` مشتق می‌شود که همین الان SELECT می‌شود |
| ۶ — بازنگری دستی | **از قبل هست، بازاستفاده شود** |
| ۷ — سلسله‌مراتب | `project > organization` هست؛ `global` نیست |
| ۸ — صفحهٔ قیمت روزانه | `categories()` فقط `provider_items` را می‌خواند |
| ۹ — rollup مالی | ماشینش کار می‌کند؛ فقط ورودی ندارد |

دربارهٔ فاز ۸، کوئری موجود در `repositories/material_prices.py` این است:

```sql
SELECT category, count(*) AS item_count, ...
  FROM provider_items
 WHERE organization_id=%s AND project_id=%s
 GROUP BY category
```

تجهیزات در `finance_resources` زندگی می‌کنند، پس با این کوئری هرگز نمی‌توانند دیده شوند.
تشخیصِ بریف دقیق بود.

### فایل‌هایی که باید تغییر کنند

- `repositories/material_prices.py` — افزودن دستهٔ `equipment` به `categories` و `latest_observations`
- `services/material_prices.py` — همان دسته در لایهٔ سرویس
- `repositories/items_and_estimates.py` — کوئری `ASSIGNMENTS` فقط از مسیر مصالح قیمت می‌گیرد و اصلاً `price_versions` را نمی‌بیند
- `router.py` — endpointهای «قیمت‌گذاری تجهیزات» (فاز ۳)
- یک ماژول تازه برای محاسبهٔ مقدار از مدت برنامه

## ۵. سه تصمیم که کد نمی‌تواند بگیرد

### الف) فرمول فاز ۴ مدتِ تقویمی می‌دهد، نه کاری

`task_start` و `task_finish` در `finance_mpp_rows` از نوع **متن** ISO-8601 هستند
(`2025-08-19T08:00`). فاصلهٔ آن‌ها شب و تعطیلات را هم می‌شمارد.

نمونهٔ مستقیم از `msp_tasks`، که مدت کاریِ محاسبه‌شدهٔ خودِ MS Project را دارد:

| `duration` (کاری) | فاصلهٔ تقویمی | اختلاف |
|---|---|---|
| `7.0000 d` | 7.375 d | +۵٪ |
| `15.0000 d` | 17.375 d | **+۱۶٪** |
| `722.8000 d` | ~900 d | **+۲۵٪** |

برای تسک‌های برگ، فاصلهٔ تقویمی همیشه از مدت کاری بزرگ‌تر یا مساوی است، پس خطا یک‌طرفه است:
بیش‌برآورد ساعت تجهیزات.

**چرا نمی‌شود ساده گرفت و از `msp_tasks.duration` خواند:** `finance_mpp_rows` این ستون را
حمل نمی‌کند، و `finance_mpp_source_versions` هیچ پیوندی به `msp_snapshots` ندارد — با
`source_sha256` شناخته می‌شود. `msp_tasks` هم با `snapshot_id` اسکوپ می‌شود نه `project_id`.
این جدایی عمدی است (مهاجرت 0011: مالکیتِ مالی بر داده‌های خودش).

> تلاش کردم اختلاف را روی تجهیزات terrace اندازه بگیرم و از راه `uid` به `msp_tasks` join
> زدم. نتیجه غیرقابل‌اتکا بود، چون `uid` بین snapshotهای مختلف یکتا نیست و join به فایل
> دیگری می‌خورد. عددش را اینجا نیاورده‌ام. همین ناتوانی، خودش یکی از یافته‌هاست.

**دو راه:**

1. فرمول تقویمیِ بریف پذیرفته شود — بدون مهاجرت، با بیش‌برآورد تا ۲۵٪ روی تسک‌های بلند.
2. ستون `task_duration_days` هنگام وارد کردن فایل در `finance_mpp_rows` نوشته شود — مهاجرت
   لازم دارد و فایل باید دوباره وارد شود، ولی مرز ماژول را حفظ می‌کند و عدد درست می‌دهد.

### ب) قانون day→hour وجود ندارد

```sql
SELECT count(*) FROM finance_unit_conversion_rules
 WHERE (from_unit='day' AND to_unit='hour') OR (from_unit='hour' AND to_unit='day');
→ 0
```

ضمناً `day` بُعدش `equipment_time` است و `hour` بُعدش `time`، یعنی عبور از بُعد — که بدون
قانون صریح ممنوع است و `can_convert('day','hour')` مقدار `False` برمی‌گرداند.

این دقیقاً رفتاری است که فاز ۴ خواسته (`missing_conversion_rule` به‌جای حدس‌زدن ۸)، ولی
پیامدش را باید دانست: **تا وقتی کسی این قانون را ثبت نکند، هر ۱۸ تجهیز ساعتی بی‌مقدار
می‌مانند.** ثبت قانون یک عمل کاربری است، نه بخشی از پیاده‌سازی.

### ج) سطح `global` وجود ندارد

```sql
CHECK (scope_kind = ANY (ARRAY['organization', 'project']))
```

فاز ۷ سه سطح می‌خواهد (`global > organization > project`). افزودن `global` مهاجرت می‌خواهد.

نکتهٔ جانبی: `finance_price_categories` سطح `global` را **دارد**. یعنی دو جدول در همین
دامنه، دو واژگان متفاوت برای «سطح» دارند. این ناسازگاری مستقل از Mission C وجود دارد و
ارزش رفع جداگانه را دارد.

---

## ۶. آیا مهاجرت لازم است؟

برای بخش عمدهٔ کار **نه**:

- `equipment` از قبل در CHECK هست
- `price_versions` آماده است
- `estimate_revisions` آماده است
- `quantitySource` مشتق‌شدنی است و ستون تازه نمی‌خواهد

مهاجرت فقط برای دو موردِ اختیاریِ بالا لازم می‌شود: `global` در `scope_kind`، و
`task_duration_days` اگر مدت کاری خواسته شود.

اگر تصمیم این باشد که «فرمول تقویمی پذیرفته و `global` رها شود»، کل Mission C **بدون هیچ
مهاجرتی** قابل پیاده‌سازی است.

## پیوست — شواهد خام

### ردیف‌های MPP، به تفکیک نوعِ فایل (پروژهٔ terrace)

| `resource_type` | سطر | `quantity` پرشده | نرخ صفر | هزینهٔ تخصیص صفر | `task_start` | `task_finish` | `source_assignment_units` |
|---|---:|---:|---:|---:|---:|---:|---:|
| `WORK` | 1278 | 0 | 1278 | 1278 | 1278 | 1278 | 1278 |
| `MATERIAL` | 867 | 0 | 0 | 0 | 867 | 867 | 867 |
| (خالی) | 221 | 0 | 221 | 221 | 221 | 221 | 35 |

`finance_mpp_rows.resource_type` نوعِ **فایل** است نه نوع مالی. MS Project نوعی به نام
equipment ندارد؛ تجهیزات در فایل از نوع `WORK` هستند. پس ادعای فاز ۴ تأیید می‌شود: برای
تجهیزات مقدار خالی است و نرخ و هزینه صفر، ولی **تاریخ شروع، تاریخ پایان و ضریب تخصیص روی
هر ۱۲۷۸ سطر موجود است** — یعنی فرمول قابل محاسبه است.

### دامنهٔ مقادیر روی تخصیص‌های تجهیزات

`source_assignment_units` بین `0.0` تا `3.0` است — ضریبی سالم، نه عددی مثل `3538.11` که
روی سطرهای `MATERIAL` دیده می‌شود. فاصلهٔ تقویمی بین `0.38` تا `220` روز.

### `weight_time` برای مقدار به کار نمی‌رود

نمونه: `0.9621279062192561` و `0.3207093020730838`. ضریب وزن‌دهی در بازهٔ ۰ تا ۱ است، نه
مدت. هشدار بریف درست است.
