# درخواست از تیم Core — یک ردیف مجوز

**مالک:** تیم Core · **اولویت:** بحرانی · **حجم کار:** یک ردیف + انتساب نقش

---

## آنچه لازم داریم

```
module_key = finance_report
action_key = issue
code       = finance_report.issue
```

همین. ماژول مالی فقط به **قرارداد کد** نیاز دارد.

## چرا

مجوز صدور گزارش رسمی مالی — عملیاتی که یک عدد را **تثبیت و منجمد** می‌کند.

**تأییدشده با خواندن فقط‌خواندنی:** هسته امروز چهار مجوز مالی دارد و این یکی را ندارد.

```
finance.view · finance.edit · finance_report.view · finance_report.export
```

## چرا با مجوز موجود جایگزین نمی‌شود

| جایگزین پیشنهادی | چرا رد است |
|---|---|
| `finance_report.export` | خروجی‌گرفتن = **خواندن** یک گزارش موجود. صدور = تثبیت رسمی یک عدد و Pin کردن ورودی‌هایش برای همیشه |
| `finance.edit` | ویرایش یک ردیف برآورد و صدور سند رسمی، دو مسئولیت متفاوت‌اند |
| `finance_report.view` | خواندن است، نه نوشتن |

> صدور گزارش تنها عملیاتی است که **ورودی‌ها را منجمد می‌کند**: نسخه قیمت، Snapshot پیشرفت و
> متن کامل گزارش در همان لحظه Pin می‌شوند و تغییرناپذیر می‌مانند. مجوزش باید به همان اندازه
> مشخص باشد.
>
> هر نگاشتِ جایگزین، دسترسی را **گسترده‌تر از قصد** می‌کند — و این گستردگی در هیچ لاگی دیده
> نمی‌شود، فقط در روزی که کسی گزارشی صادر کند که نباید می‌کرد.

## رفتار فعلی — و درست است

```
POST /projects/{id}/finance/report-snapshots  →  403
```

چون کد در کاتالوگ نیست، **هیچ کاربری نمی‌تواند داشته باشد**. رابط کاربری هم دکمه «ثبت گزارش
دوره‌ای» را نشان نمی‌دهد، چون همان مجوزهایی را می‌خواند که سرور رویشان تصمیم می‌گیرد.

یک تست این را قفل کرده: اگر مسیر دیگری مجوز غایب بخواهد، یا این مسیر به کد ضعیف‌تری تنزل
کند، تست شکست می‌خورد.

**تا آن روز، بسته می‌ماند. این را دور نزنید.**

---

## تصمیمی که مال شماست

**کدام نقش‌ها این مجوز را بگیرند، تصمیم محصول/Core است — نه ماژول مالی.**

نکته‌ای برای بحث: `org_chief` منطقی‌ترین کاندید است. آیا `finance_expert` هم باید بگیرد؟

## نمونه SQL

> ## ⚠ REFERENCE ONLY — CORE TEAM MUST REVIEW
> **اجرا نشده و نباید توسط ماژول مالی اجرا شود.** فقط برای اینکه شکل ردیف روشن باشد.

```sql
-- REFERENCE ONLY
INSERT INTO permissions (module_key, action_key, code, label, group_name)
VALUES ('finance_report', 'issue', 'finance_report.issue',
        'صدور گزارش رسمی مالی', 'مالی');

-- REFERENCE ONLY — انتساب نقش، پس از تصمیم محصول
INSERT INTO role_permissions (role_id, permission_id)
SELECT r.id, p.id FROM roles r, permissions p
 WHERE r.code = '<نقش تأییدشده>' AND p.code = 'finance_report.issue';
```

## معیار پذیرش

```
□ ۱. ردیف permissions با هر سه مقدار بالا موجود است
□ ۲. نقش‌های تأییدشده آن را دارند
□ ۳. نقش‌های دیگر آن را ندارند
□ ۴. سلب فردی (user_permission_overrides.allowed = false) همچنان غالب است
□ ۵. POST report-snapshots فقط برای کاربر مجاز ۲۰۰ می‌دهد — بقیه ۴۰۳
```

بند ۴ مهم است: قاعده «سلب صریح بر اعطای نقش غلبه می‌کند» نباید با افزودن این مجوز بشکند.

**پس از انجام، به ما خبر دهید.** هیچ تغییری در ماژول مالی لازم نیست — کد از همان لحظه کار
می‌کند.
