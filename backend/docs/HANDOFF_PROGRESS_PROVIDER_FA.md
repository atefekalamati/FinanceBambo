# درخواست از تیم Progress — مقدار اجراشده

**مالک:** تیم Progress · **اولویت:** بحرانی — بدون این، گزارش‌ها بدون پیشرفت‌اند

---

## مسئله، در یک جمله

هسته می‌گوید یک Task **۳۰٪ انجام شده**؛ نمی‌گوید آن ۳۰٪ **چند کیلوگرم میلگرد** است. و
ماژول مالی برای تبدیل پیشرفت به پول، دقیقاً به دومی نیاز دارد.

## آنچه بررسی شد

هر ۳۰ ستون `msp_tasks` خوانده شد:

```
✅ نام، WBS، outline_number، تاریخ‌ها
✅ percent_complete، percent_work_complete، physical_percent_complete
❌ ستون منبع            ← وجود ندارد
❌ ستون واحد            ← وجود ندارد
❌ مقدار برنامه‌ای/اجراشده ← وجود ندارد
❌ جدول تخصیص منبع      ← اصلاً وجود ندارد
```

---

## آنچه ماژول مالی هرگز استنتاج نمی‌کند

چهار میان‌بر بررسی و **رد** شدند. هر چهار عدد تولید می‌کنند و هر چهار دروغ می‌گویند:

| میان‌بر | چرا رد شد |
|---|---|
| `درصد Task × مقدار برآورد` | عددی می‌سازد که **همیشه با برآورد می‌خواند** — سنجه‌ای که هرگز نمی‌تواند مشکلی را لو بدهد |
| `percent_work_complete` | تلاش را اندازه می‌گیرد، نه سهمی از یک مقدار فیزیکی |
| `duration` / `work` | مدت زمان، مقدار نیست |
| ساختن `assignmentExternalId` مصنوعی | ارتباطی جعل می‌کند که هسته ادعایش را ندارد |

## قرارداد داده‌ای که لازم داریم

### سرآیند Snapshot

```
hostSnapshotId        bigint   ← msp_snapshots.id
hostFileVersionId     bigint   ← msp_file_versions.id
projectId             text
reportingDate         ISO date ← ترجیحاً تاریخ وضعیت برنامه‌ریز، نه تاریخ آپلود
status                ready | superseded
source                mpp | host_feed | synthetic
```

### هر ردیف تخصیص

```
activityCode          text          ← تطبیق با خط برآورد
resourceCode|Id       text          ← کدام منبع
unit                  text          ← واحد همان منبع
plannedQuantity       numeric|null  ← اگر معتبر است
actualQuantity        numeric|null  ← این عدد، پول می‌سازد
progressPercent       numeric|null  ← اگر جدا در دسترس است
quality|confidence    عدد یا برچسب  ← اختیاری
```

---

## قاعده‌ای که نباید شکسته شود

> ### `null` و `0` یکی نیستند
>
> ```
> actualQuantity = null  →  «اندازه‌ای در دست نیست»
> actualQuantity = 0     →  «اندازه گرفتیم، هیچ اجرا نشده»
> ```
>
> اگر مقداری ندارید، **`null` بفرستید**. صفر نفرستید.

`actualQuantity` **می‌تواند null باشد** و این حالت پشتیبانی‌شده است.

### رفتار ماژول مالی در نبود مقدار

```
خط گزارش      →  unavailable
هشدار         →  PROGRESS_MISSING
calculationStatus →  incomplete
سنجه‌های وابسته →  null، نه عددی کمتر از واقعیت
```

**هرگز صفر بی‌صدا.** این قاعده امروز پیاده و تست‌شده است و تغییر نمی‌کند.

---

## چرخه حیات

```
Core / Progress module
      ↓  خوراک با مقدار
ProgressSnapshotProvider   ← شما این را پیاده می‌کنید
      ↓
Finance adapter
      ↓
محاسبه گزارش
```

**ماژول مالی نسبت به منبع پیشرفت فقط‌خواندنی است.** چیزی نمی‌نویسد، چیزی Parse نمی‌کند.

## دو قاعده پیاده‌سازی که اشتباه‌شان گران است

**۱. با همان شناسه‌ای جواب بدهید که با آن پرسیده شده.** ماژول مالی Header را با شناسه‌ای که
فرستاده تطبیق می‌دهد، و وقتی ردیف ارجاع `host_snapshot_id` دارد با همان bigint می‌پرسد.
برگرداندن شناسه دیگری، یک درخواست معتبر را «Snapshot پیدا نشد» می‌کند.

> این اشتباه در چهار نقطه از کد خودمان بود و هر چهار جا اصلاح شد.

**۲. در نبود Snapshot، `None` برگردانید — نه Header خالی.** Header خالی ادعا می‌کند «این
همان Snapshot است» و بعد هیچ Snapshotی را توصیف نمی‌کند.

# ❓ یک پرسش برای تیم برنامه‌ریزی

> ## کدام فیلد MSP، کد فعالیت معتبر BAMBO است؟

امروز یک زنجیره **قابل تنظیم** داریم، و پیش‌فرضش یک **حدس مستندشده** است — نه یک واقعیت:

```
text1  →  outline_number  →  wbs
```

`Text1` در ادغام‌های MSP معمولاً کد فعالیت را نگه می‌دارد، ولی این یک **قرارداد
برنامه‌ریزی** است، نه ستونی که هسته برایش نامی داشته باشد.

**ما بدون تأیید شما هیچ‌کدام را معتبر اعلام نمی‌کنیم.**

### پاسخ مورد انتظار

```
فیلد معتبر : <text1 | outline_number | wbs | number1 | ...>
پایدار است بین Snapshotها؟ : بله / خیر
همیشه پر است؟             : بله / خیر
نمونه مقدار               : <مثلاً ACT-102>
```

پس از پاسخ، یک خط پیکربندی است — بدون تغییر در API:

```python
CoreProgressSnapshotProvider(conn, activity_code_fields=("<فیلد شما>",))
CoreProjectActivityProvider(conn,  activity_code_fields=("<فیلد شما>",))
```

هر دو باید **یک ترتیب** بگیرند، وگرنه به یک خط برآورد کد فعالیتی پیشنهاد می‌شود که خوراک
پیشرفت هرگز نمی‌سازد.

> **حدس اشتباه در این فیلد، به‌صورت خطوط unmapped دیده می‌شود — که آشکار است.** خطر واقعی
> تطبیق اشتباه است، که دیده نمی‌شود.

---

## معیار پذیرش

```
□ ۱. Snapshot با شناسه bigint هسته قابل بازیابی است
□ ۲. نگاشت فعالیت صریح است (فیلد تأییدشده)
□ ۳. نگاشت منبع و واحد صریح است
□ ۴. مقدار فیزیکی اجراشده قابل تأمین است
□ ۵. نبودِ مقدار، null می‌ماند — نه صفر
□ ۶. ماژول مالی هیچ MPP را Parse نمی‌کند
□ ۷. هیچ اجرای ساختگی از روی برآورد ساخته نمی‌شود
```

---

## یک نقص باز که باید بدانید

وقتی تطبیق به کد فعالیت برمی‌گردد (چون تخصیصی در کار نیست)، **دو خط برآورد روی یک فعالیت
با یک ردیف تطبیق می‌خورند**.

در حالت فعلی زیانی ندارد — بدون مقدار، هر دو `unavailable` می‌شوند. ولی Providerی که مقدار
سطح-Task بدهد، به هر دو خط یک عدد می‌دهد بدون توجه به منبع.

**در داده نمایشی واقعاً رخ داد:** یک اصلاح دستی برای قالب‌بندی، روی آرماتوربندی هم اعمال شد
و پیش‌بینی نیروی انسانی ۲٫۱ میلیارد تومان بالا آمد.

اگر ردیف‌هایتان `resourceCode` داشته باشند، این مسئله از بین می‌رود — و این یکی از دلایل
اهمیت بند ۳ است.

# ❓ پرسش دوم — آیا `sourceMethod` را می‌فرستید؟

**وضعیت امروز: هیچ Providerی این فیلد را نمی‌فرستد.** بررسی شد، حدس نیست.

## آنچه اندازه گرفتیم

خوراک واقعی از هر دو Provider گرفته شد (نه از فایل نمونه)، برای پروژهٔ terrace،
۷۲۷ تخصیص در هرکدام. کلیدهای هر ردیف پیش از آنکه مالی دستش بزند:

| فیلدی که قرارداد اجباری می‌داند | `FinanceRowsProgressProvider` | `CoreProgressSnapshotProvider` |
|---|---|---|
| `assignmentExternalId` | ✅ ۷۲۷/۷۲۷ | ✅ ۷۲۷/۷۲۷ |
| `resourceExternalId` · `resourceName` | ✅ | ✅ |
| `unit` · `plannedQuantity` · `actualQuantity` · `remainingQuantity` | ✅ | ✅ |
| `plannedWork` · `actualWork` · `remainingWork` | ✅ | ✅ |
| `activityExternalId` | ❌ **غایب** (کد فعالیت زیر `task.activityCode` است) | ❌ **غایب** |
| `percentWorkComplete` | ❌ **غایب** (نامش `assignmentWorkCompletePercent` است) | ❌ **غایب** |
| **`sourceMethod`** | ❌ **غایب روی هر ۷۲۷ ردیف** | ❌ **غایب روی هر ۷۲۷ ردیف** |
| `quality` | ❌ غایب | ❌ غایب |
| `warnings` | ❌ غایب | ❌ غایب |
| `measurementType` | ❌ غایب | ❌ غایب |

Providerهای سوم و چهارم (`MppFileProgressProvider` و Provider دادهٔ کاشته) هم هیچ‌کدام
این نام‌ها را نمی‌سازند — رشتهٔ `sourceMethod` در هیچ Providerی وجود ندارد.

## پس امروز چیزی از بین نمی‌رود

`services/progress.py` مقدار محاسبه‌شدهٔ خودش را روی `row["sourceMethod"]` می‌نویسد.
چون خوراک این کلید را ندارد، آن نوشتن **ایجاد** است نه **رونویسی**؛ هیچ ادعایی از
دست نمی‌رود چون هیچ ادعایی نیامده.

یک نکتهٔ ساختاری که خوب است بدانید: در استقرار فعلی، مالی خودش خوراک را از جدول‌های
همین دیتابیس می‌سازد. هیچ Providerی کلاینت HTTP نیست و سرویس پیشرفتِ دوری وجود ندارد
که چیزی بفرستد. قرارداد کیت شکل سیم بین دو سرویس را توصیف می‌کند؛ آن سیم هنوز کشیده نشده.

## چرا با این حال می‌پرسیم

روشِ انتخاب‌شده مستقیماً عدد کیفیت را می‌سازد و کیفیت در ارقام مالی می‌نشیند:

```
assignment_actual         1.0
assignment_work_percent   0.8
task_progress_fallback    0.6
```

اگر روزی Providerی این فیلد را بفرستد و با محاسبهٔ ما فرق داشته باشد، امروز **بی‌صدا**
محاسبهٔ ما برنده می‌شود. آن روز باید مقایسه کنیم و اختلاف را هشدار بدهیم، نه اینکه یکی
را بی‌سروصدا دور بریزیم — و محاسبهٔ خودمان هم باید بماند، چون تنها چیزی است که وقتی
فیلد نیامد جواب می‌دهد.

## آنچه از شما می‌خواهیم بدانیم

۱. آیا Provider آیندهٔ شما `sourceMethod` را روی هر تخصیص می‌فرستد؟
۲. اگر بله، واژگانش دقیقاً چیست؟ نردبان ما این پنج را می‌سازد:
   `manual_override` · `assignment_actual` · `assignment_work_percent` ·
   `task_progress_fallback` · `missing`.
   قرارداد کیت `excel_import` و `manual_entry` را هم نام می‌برد؛ آن دو در مالی روی
   **خط برآورد** می‌نشینند نه روی تخصیص، و اگر شما هم همین را می‌فهمید بگویید.
۳. آیا `quality` را خودتان می‌فرستید یا انتظار دارید ما بسازیم؟ اگر هر دو بفرستیم،
   کدام معتبر است؟
۴. نام‌ها را تثبیت کنید: ما `assignmentWorkCompletePercent` و `task.activityCode`
   می‌سازیم، کیت `percentWorkComplete` و `activityExternalId` می‌گوید. یکی از این دو
   باید عوض شود و بهتر است پیش از اولین اتصال واقعی باشد.

## و یک کار سمت ما، به‌محض اینکه پاسخ «بله» باشد

قرارداد منتشرشدهٔ ما شکل تخصیص را **اصلاً اعلام نکرده**:

```
ProgressFeedResponse.properties.assignments.items = { "type": "object", "additionalProperties": true }
```

این تنها آرایهٔ باز در کل `contracts/openapi.json` است. یعنی اگر نام فیلدی عوض شود،
ما خطا نمی‌دهیم؛ بی‌صدا یک پله پایین‌تر می‌افتیم. از ۱۶ فیلد اجباری کیت، مصرف‌کننده‌های
ما امروز این هفت‌تا را **هرگز نمی‌خوانند**:

```
plannedWork · remainingQuantity · remainingWork · unit
resourceExternalId · resourceName · sourceMethod
```

تا وقتی هیچ‌کس چیزی نمی‌فرستد این بی‌ضرر است. با اولین Provider واقعی، بی‌ضرر نیست.

> **یادداشت صداقت:** متن Integration Kit v1.1 در این مخزن نیست، پس نقل‌قول‌های
> قراردادی بالا از گزارش بازبینی گرفته شده‌اند. آنچه در این سند اندازه‌گیری شده،
> فقط سمت ماست: کد، Providerها و خوراک واقعی.
