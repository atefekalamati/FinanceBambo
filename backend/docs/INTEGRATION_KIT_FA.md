## ۲. ماژول مالی چه چیزی هست و چه چیزی نیست

**یک کتابخانه است، نه یک سرویس.** ریشهٔ ترکیبی ندارد، هیچ متغیر محیطی نمی‌خواند، و
نمی‌داند چه کسی Portهایش را پیاده کرده. میزبان BAMBO چهارده کلید روی `application.state`
می‌گذارد و ماژول کار می‌کند.

**احراز هویت را پیاده نمی‌کند.** درزِ هویت یک Protocol است:

```python
class AuthProvider(Protocol):
    async def current(self, request: Request) -> AuthContext: ...
```

میزبان این یک تابع را می‌نویسد. `app/` و `coreint/` **هیچ هدر درخواستی را نمی‌خوانند** — و
دو آزمون در `tests/test_demo_isolation.py` این را نگه می‌دارند، چون `X-Demo-User` که در
`devhost` هست روی یک میزبان واقعی معنایش جعل هویت هر کسی است که شناسه‌اش را حدس بزند.

## ۳. نصب روی یک دیتابیس تازه

```bash
cd backend

# ۱. پیش‌بررسی — فقط‌خواندنی، هیچ‌چیز اعمال نمی‌شود
python -m scripts.install_preflight --dsn "<DSN>"

# ۲. پشتیبان. همیشه. جزئیات در BACKUP_RESTORE_RUNBOOK_FA.md
pg_dump --format=custom --file=<backup>.dump "<DSN>"

# ۳. schema
FINANCE_MIGRATION_DSN="<DSN>" alembic upgrade head      # باید 0019 بدهد

# ۴. ثابت‌های مالی — فقط‌خواندنی
python scripts/verify_finance_invariants.py --dsn "<DSN>"
```

مرحلهٔ ۱ **پیش‌شرط Core را زود می‌گوید، نه دیر**: revision 0009 یک کلید خارجی واقعی به
`msp_tasks` که مالکش Core است اعلام می‌کند. بدون پیش‌بررسی، این نبودن هشت revision بعد
کشف می‌شود — بعد از چند دقیقه DDL روی یک دیتابیس به اندازهٔ تولید. اجرا یک تراکنش است و
تمیز برمی‌گردد، ولی اپراتور یک پیش‌شرط پنج‌ثانیه‌ای را از راه سخت یاد می‌گیرد.

**این مخزن migration مالِ Core را ندارد.** `scripts/demo/core_mirror.sql` یک **آینهٔ
نمایشیِ تولیدشده** است و سرصفحهٔ خودش می‌گوید هرگز روی دیتابیس Core اعمال نمی‌شود. اگر
`msp_tasks` نبود، جوابْ گرفتن migration خودِ Core از تیم میزبان است، نه ساختنش از اینجا.

## ۴. ارتقای یک دیتابیس مشترکی که از قبل داده دارد

**قاعده‌ای که نقض نمی‌شود: یک dump راهِ ارتقا نیست.** `pg_restore` یک دیتابیس را
**جایگزین** می‌کند — شکل درست برای پشتیبان و نصب تازه، و شکل کاملاً غلط برای دیتابیسی که
جدول‌های Core و ردیف‌های واقعی سایت را دارد.

راه ارتقا فقط این است:

```
□ install_preflight سبز
□ پشتیبان تازه گرفته شد و اندازه‌اش منطقی است
□ alembic current خوانده شد و ثبت شد   ← وضعیت فعلی مقصد: 0016
□ alembic upgrade head                  ← 0017 و 0019 اجرا می‌شوند
□ alembic current دوباره              ← باید 0019 بدهد
□ verify_finance_invariants قبل و بعد، و دو خروجی مقایسه شد
□ یک sync از نوع refresh              ← بند ۶
```

### انتقال رکورد، اگر لازم شد

`scripts/transfer_approved_records.py` — فهرست `APPROVED` آن **عمداً خالی است**. پر کردنش
یک تصمیم تجاری است دربارهٔ اینکه کدام ردیف اجازه دارد از یک دیتابیس آزمایشی بیرون بیاید، و
کسی این تصمیم را نگرفته. ابزار تا آن موقع چیزی منتقل نمی‌کند و صریحاً می‌گوید چرا.

آنچه به‌طور ساختاری رد می‌کند: مقصدی که loopback نیست · نوشتن بدون `--apply` · هر ردیفی که
هویت ساختگی، نقش نمایشی یا منبع probe باشد (با الگو **و** با شناسهٔ صریح) · عبور از مرز
سازمان/پروژه. و `invoices` و `report_snapshots` در فهرست جداول قابل‌انتقال **نیستند**: سندی
که در یک دیتابیس آزمایشی ساخته شده در یک دفتر واقعی جایی ندارد.

هر نوشتن `ON CONFLICT DO NOTHING` است روی هویت scope‌دار خود جدول، پس اجرای دوم چیزی
منتقل نمی‌کند و می‌گوید چه چیزی را match کرد.

## ۵. منبع MPP — پیکربندی و قاعدهٔ انتخاب

### پیکربندی

| متغیر | معنا |
|---|---|
| `MPP_IMPORT_ROOT` | ریشهٔ ذخیره‌سازیِ تأییدشده. **بدون ویرایش کد قابل تغییر است** — از `os.environ` و بعد `.env` خوانده می‌شود |
| `MPP_IMPORT_ENABLED` | تا وقتی `true` نباشد، import خاموش است |
| `MPP_MAX_FILE_SIZE_MB` | پیش‌فرض ۱۰۰ |
| `MPP_IMPORT_INTERVAL_MINUTES` | فاصلهٔ tick دوره‌ای |
| `MPP_JAVA_HOME` | JRE برای MPXJ — بند ۷ |

### پشتیبانی از ذخیره‌سازی

**فایل‌سیستم محلی (یا هر مسیری که سیستم‌عامل mount کرده).** ماژول یک **مسیر** می‌گیرد و
`Path.open` می‌زند. object storage پشتیبانی **نمی‌شود**: ارجاع به یک شیء راه‌دور مسیر
فایل‌سیستم نیست و این ماژول تظاهر نمی‌کند که هست. اگر روزی لازم شد، درِ ورودی یکی است
(`coreint/mpp_files.py`) و همان‌جا عوض می‌شود.

### قاعدهٔ انتخاب منبع

**نسخهٔ ready پروژهٔ خودش، تازه‌ترین import‌شده.** در یک جا نوشته شده
(`app/finance/domain/mpp_source_version.py`) چون چهار سرویس جواب را می‌خواستند و هر کدام
کپی خودش را داشت — کپی‌هایی که با هم می‌خواندند، که خطرناک‌ترین نوع تکرار است.

scope بخشی از قاعده است: نسخهٔ پروژه یا سازمان دیگر هرگز جواب نیست، و پروژه‌ای که چیزی
import نکرده **هیچ نسخهٔ فعالی ندارد**، نه نسخهٔ کسی دیگر.

`status = 'ready'` است که import نیمه‌کاره را بیرون نگه می‌دارد.

**این راهی برای درخواست یک نسخهٔ خاص نیست.** گزارشی که به نسخه‌ای pin شده، مقایسهٔ
baseline، یا snapshot در حال بازپخش، نسخه را **نام می‌برد** — و نام‌بردن هم scope‌دار است.
`finance_progress._BY_ID` آن مسیر است و عمداً هیچ ترتیبی ندارد: انتخاب صریح مسابقهٔ تاریخ‌ها
نیست. **هیچ منبعِ تاریخیِ pin‌شده‌ای بی‌صدا جایگزین نمی‌شود.**

### بازنویسی و حذف

| رخداد | رفتار |
|---|---|
| همان بایت‌ها، دوباره | `unchanged` — همان نسخه، هیچ ردیفی نوشته نمی‌شود |
| همان بایت‌ها، نام دیگر | `unchanged` — فقط برچسب نام به‌روز می‌شود؛ هویتِ محتوا و تاریخ دست‌نخورده |
| بایت‌های دیگر، همان نام | نسخهٔ **جدید**. نسخهٔ قبلی و ردیف‌هایش می‌مانند |
| فایل حذف شد | نسخه و ردیف‌هایش می‌مانند. provenance تاریخی پاک نمی‌شود |
| فایل در حال رسیدن | `MPP_FILE_NOT_STABLE` — بند ۶ |
| ارزِ تصمیم‌نگرفته | `MPP_CURRENCY_UNRESOLVED` و **وضعیت معتبر قبلی کامل حفظ می‌شود** |

## ۶. چرخهٔ عمر نسخه — آنچه اثبات شده و آنچه نشده

### اثبات‌شده روی کپی ایزوله

| سناریو | نتیجه |
|---|---|
| تلاش مجدد یکسان | `unchanged`، هیچ نوشتنی |
| نام عوض‌شده با محتوای یکسان | `unchanged`، فقط برچسب |
| بایت‌های عوض‌شده در همان مسیر | تشخیص داده شد (با sha، نه با نام یا زمان یا برچسب نسخه) |
| ارز مبهم | رد شد؛ هر دو نسخهٔ قبلی، ۱۵۷۸ ردیف، ۸۳۸ خط برآورد و نسخهٔ فعال دست‌نخورده |
| دو sync هم‌زمان | هر دو `unchanged`، شمارش‌ها ثابت |
| دو `refresh` هم‌زمان (حذف + بازنویسی) | هر دو `refreshed`، همان ۷۸۹ ردیف، `stated == actual` — قفل ردیفی Postgres سریالی‌شان می‌کند |
| فایل در حال نوشته‌شدن | `MPP_FILE_NOT_STABLE` |
| فایل عوض‌شده بین hash و parse | `MPP_FILE_NOT_STABLE`، هیچ ردیفی نوشته نمی‌شود |

### محدودیت‌هایی که صریح گفته می‌شوند

- **فایلی که ناقص رسید و بعد متوقف شد** تشخیص داده نمی‌شود، چون دیگر تغییر نمی‌کند.
  اندازه‌گیری‌شده: parser آن را با `MPP_FILE_CORRUPTED` رد می‌کند، پیش از نوشتن هر ردیف و
  داخل همان یک تراکنش، پس وضعیت معتبر قبلی می‌ماند. محافظ دربارهٔ فایلی است که **در حال
  رسیدن** است، نه هر فایل ناقصی.
- **اتمیک‌بودن بین‌سرویسی وجود ندارد و ادعا نمی‌شود.** sync مالی یک تراکنش Postgres است، پس
  **سمت Finance** یا کامل است یا هیچ. اگر Core موفق شود و Finance شکست بخورد، Core جلو رفته
  و Finance نرفته — و تعمیرش **اجرای دوبارهٔ sync** است، که چون sha کلید idempotency است
  بی‌خطر و تکرارپذیر است. هیچ commit دوفازی، هیچ saga، هیچ جبران خودکار.
- **هم‌زمانی روی یک فایل جدیدِ پذیرفتنی آزمون نشده.** دروازهٔ ارز فقط دو sha تأییدشده را
  می‌پذیرد و افزودن sha یک تصمیم تجاری است. **BLOCKED**، حدس نزده.
- **رویدادهای بی‌ترتیب میزبان** روی یک میزبان واقعی آزمون نشده. آنچه محلی اثبات شده این است
  که ترتیب اهمیتی ندارد چون هویت از **محتوا** می‌آید نه از زمان رسیدن: همان بایت‌ها همان
  نسخه است هر چند بار و به هر ترتیبی که برسد.

### پس از افزودن ستون، یک refresh لازم است

`0019` ستون `source_fixed_cost_irr` را اضافه می‌کند و روی ردیف‌های موجود NULL است. `refresh`
دقیقاً برای همین وجود دارد: فایل تغییرنکرده را دوباره می‌خواند و ردیف‌های همان نسخه را
جایگزین می‌کند **بدون دست زدن به سطر نسخه**، پس هر `progress_snapshot_refs` و هر گزارشی که
آن نسخه را pin کرده هنوز resolve می‌شود. گزارش‌های صادرشده از اساس مصون‌اند:
`report_snapshots.snapshot_payload` کل تغذیه را در لحظهٔ صدور منجمد می‌کند.

## ۱۰. معیارهای پذیرش

میزبان وقتی می‌تواند بگوید یکپارچه‌سازی موفق بود که هر هفت مورد برقرار باشد:

```
□ install_preflight روی مقصد سبز است
□ alembic current روی مقصد 0019 می‌دهد، و head یکی است
□ verify_finance_invariants روی مقصد: ۰ FAIL
□ یک refresh اجرا شد و source_fixed_cost_irr روی ردیف‌های نسخهٔ فعال پر است
□ GET /finance/summary با finance.view → 200
□ GET /finance/reports/live با finance_report.view → 200، و با finance.view تنها → 403
□ POST /finance/invoices با finance.manage_invoice → 201، و با finance.edit → 403
```

سطر آخر همان چیزی است که ثبت‌نشدنِ `finance.manage_invoice` را آشکار می‌کند: اگر ثبت نشده
باشد، هر دو نیمه ۴۰۳ می‌دهند و قابلیت خاموش است بدون اینکه چیزی خراب به نظر برسد.

## ۱۱. محدودیت‌های بازگشت

`downgrade` برای هر revision نوشته و آزموده شده، و `0019` روی PG16 و PG18 با بازگشت دقیق
به اثرانگشت قبلی اثبات شد. ولی:

- **downgrade خط‌های برآوردی که ساخته شده‌اند را برنمی‌دارد.** رکورد مالی‌اند و حذفشان کار
  migration نیست. `downgrade 0017` ستون را می‌برد و آن سه خط `general_cost` می‌مانند.
- **دادهٔ ستون‌های خوانده‌شده از فایل با downgrade می‌رود و با یک sync دوباره برمی‌گردد.**
- **گزارش‌های صادرشده هرگز بازنویسی نمی‌شوند**، در هیچ جهتی.
- جزئیات در `ROLLBACK_RUNBOOK_FA.md`.

## ۱۲. محدودیت‌های شناخته‌شده

1. **تجهیزات در این فایل هیچ قیمتی ندارد.** پنج جا بررسی شد و هر پنج خالی است: نرخ
   استاندارد (۰ از ۱۸)، هر پنج جدول نرخ A–E (۰ از ۱۸)، baseline منبع و تخصیص، هزینهٔ تخصیص
   (۰ از ۴۲۶)، و تسکی که **فقط** تجهیزات داشته باشد (هیچ). ۴۲۶ خط برآورد بدون مبنا
   می‌مانند و گزارش `null` می‌دهد نه `0`. اگر کسب‌وکار قیمت می‌خواهد، باید از بیرون فایل
   بیاید — از جدول قیمت روز، نه از MPP.
2. **«WF ریالی» پول نیست.** `Task.Cost / WF = 32826.87` دقیقاً روی هر ۲۶۶ تسک برگ؛ یک وزن
   نرمال‌شده است و اطلاعات مستقلی ندارد.
3. **جمع برآورد جزئی است** وقتی خطی مبنا ندارد، و سه چیز این را می‌گویند:
   `incompleteMetricKeys`، `missingEstimateLineCount`، و `calculationStatus`.
4. **`contracts/openapi.json` ۹ عملیاتی که devhost اضافه می‌کند را توصیف نمی‌کند** (مسیرهای
   MPP و فایل‌های ایستا). `--check` درست پاس می‌شود چون همان `create_app()` را می‌سنجد.
   برعکسش صفر است: قرارداد زیرمجموعهٔ محضِ سطحِ سرو‌شده است.
5. **`frontend/scripts/print-audit.mjs` روی `period-report` می‌شکند** — صفحه‌ای که
   `layout-audit` صریحاً «withdrawn» می‌نامدش. نقص پیش‌موجود فرانت‌اند (روی `origin/master`
   هم همین است) و در این کار دست نزده شد.
6. **تصمیم‌های باز محصول** در `DECISION_PACKS_FA.md`. D-1 در ۲۰۲۶-۰۹-۱۲ توسط مالک نهایی
   شد: «هر سطح مجوز خودش را دارد»، و `finance.view` از درِ گزارش برداشته شد.
