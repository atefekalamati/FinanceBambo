# از فایل MSP تا گزارش مالی — قرارداد منبع و مقدار

سند مرجع. وقتی کسی می‌پرسد «این عدد از کجا آمد»، پاسخ اینجاست.

---

## مسیر

```
فایل MPP
   ↓  parser موجود Core (MPXJ) — مالی هرگز فایل نمی‌خواند
msp_snapshots · msp_tasks · msp_resources · msp_resource_assignments
   ↓  CoreProgressSnapshotProvider — فقط‌خواندنی
feed تخصیص
   ↓  ProgressPairing
خط‌های برآورد مالی
   ↓
گزارش زنده · نمای کلی · گزارش WBS
```

هر پیکان یک‌طرفه است. مالی به هیچ‌کدام از جدول‌های `msp_*` نمی‌نویسد.

---

## مالکیت

| | مالک | مالی |
|---|---|---|
| `msp_snapshots` · `msp_tasks` | Core/Planning | فقط خواندن |
| `msp_resources` · `msp_resource_assignments` | Core/Planning | فقط خواندن |
| ۱۵ جدول مالی | مالی | خواندن و نوشتن |

Alembic مالی **فقط** schema مالی را دارد. دو جدول تازه به‌صورت SQL در
[`docs/sql/`](sql/) تحویل داده می‌شوند تا تیم Core با فرایند مهاجرت خودش اعمالشان کند.
هیچ revision مالی‌ای برای آنها ساخته نشد — و `0007` وجود ندارد.

---

## هویت

```
resource_uid      هویت منبع
assignment_uid    هویت تخصیص
task_uid          هویت فعالیت
```

**GUID هویت نیست.** دو نسخهٔ ذخیره‌شده از یک زمان‌بندی واقعی مقایسه شد:

```
نام فعالیت‌ها  ۹۱۸/۹۱۸ یکسان    Task UID   ۱۲۴۸/۱۲۴۸ یکسان
کد WBS        ۱۲۴۸/۱۲۴۸ یکسان   Task GUID  ۰/۱۲۴۸ یکسان
```

ذخیرهٔ فایل تحت نام تازه، همهٔ GUIDها را باطل می‌کند بدون آنکه چیزی عوض شود. GUID فقط
برای تشخیص نگه داشته می‌شود.

**هویت فعالیت با کد فعالیت یکی نیست.** `task_uid` هویت است؛ `activityCode` از نردبان
`text1 → outline_number → wbs` می‌آید و برای تطبیق با خط برآورد به کار می‌رود. تخصیص‌ها با
`task_uid` وصل می‌شوند، نه با کد فعالیت.

هیچ قید یکتای بین‌snapshotی وجود ندارد. اگر UIDها روزی جابه‌جا شوند، نتیجه ردیف «بدون
تطابق» است — دیدنی — نه اتصال بی‌صدای اشتباه.

## مقدار

دو مقدار، دو معنا، **هرگز ادغام نمی‌شوند**:

| | معنا | کاربرد مالی |
|---|---|---|
| `msp_resources.resource_quantity` | کل مقدار منبع در پروژه | نمایش و ممیزی |
| `msp_resource_assignments.planned_quantity` | مقدار همان منبع روی همان فعالیت | **گزارش WBS** |

مقدار سطح منبع **جمعِ** مقادیر تخصیص است — روی ۱۰ منبع واقعی آزموده شد، تطابق کامل
(آرماتور: ۱٬۳۲۹٬۱۲۱٫۲۲ = ۱٬۳۲۹٬۱۲۱٫۲۲ کیلوگرم).

**مالی مقدار سطح منبع را بین فعالیت‌ها توزیع نمی‌کند.** اگر روزی فقط آن موجود باشد،
`plannedQuantity` سطح تخصیص `NULL` می‌ماند.

### مقدار از کجا نمی‌آید

```
Work · Actual Work · Duration · Percent Complete · Units · Max Units
```

`Work` ساعت است. `Units` و `Max Units` درصد ظرفیت‌اند. هیچ‌کدام کیلوگرم یا مترمکعب
نیستند. برای منبع MATERIAL، خودِ MS Project مصرف را در `Work` نگه می‌دارد و MPXJ آن را با
نام `Material` هم عرضه می‌کند — **همان یکی خوانده می‌شود، از راه `Material`**.

**`NULL` با `0` یکی نیست.** مقداری که کسی گزارش نکرده، مقداری از هیچ نیست.

## واحد

```
Material Label  → جای رسمی واحد در MS Project
Initials        → قرارداد این برنامه‌ریز
```

در فایل مرجع، **هر ۸۱ منبع `Material Label` را خالی گذاشته‌اند** و واحد را در `Initials`
نوشته‌اند: آرماتور → کیلوگرم، بتن → مترمکعب، قالب‌بندی → مترمربع.

**این استاندارد نیست.** `quantity_unit_source` ذخیره می‌شود تا فایل بعدی که `Material
Label` را درست پر کند، بی‌صدا تفسیر نشود.

نکتهٔ ظریف: برای منبع `WORK`، `Initials` حرف اول نام است (پیش‌فرض MSP)، نه واحد. واحد فقط
از منابع `MATERIAL` خوانده می‌شود.

دیتابیس مقدار بدون واحد را با یک `CHECK` رد می‌کند.

## نوع منبع

```
MSP MATERIAL → material         امن
MSP COST     → general_cost     امن
MSP WORK     → NULL             ← عمدی
```

MSP تفکیک labor از equipment ندارد. در فایل مرجع هر ۱۸ منبع WORK: `Code = null`،
`Group = "1"`. **هرگز از نام منبع استنتاج نمی‌شود** — «جرثقیل ۳۰ تن» با heuristic نامی به
نیروی انسانی تبدیل می‌شود و هیچ خطایی نمی‌دهد.

`NULL` یک حالت واقعی است. مالی آن خط‌ها را نشان می‌دهد و از تفکیک هزینه کنارشان می‌گذارد —
دیده می‌شود، برخلاف یک حدس اشتباه. **«unclassified» به چهار نوع مالی اضافه نشد.**

## مرجع پول

```
قیمت معتبر         price_versions             ← مالی
هزینهٔ واقعی معتبر  فاکتور تأییدشده             ← مالی
Std. Rate در MSP   مرجع و مقایسه               ← نه قیمت
Actual Cost در MSP مرجع و مقایسه               ← نه هزینهٔ واقعی
```

`Actual Cost` در MSP عددی است که برنامه‌ریز تایپ کرده. سند مالی نیست و جایگزین فاکتور
نمی‌شود.

## مرجع پیشرفت و ترتیب اولویت

```
۱. اصلاح دستی
۲. actualQuantity          ← مقدار فیزیکی، بهترین
۳. actualWork              ← بازگشتی ضعیف‌تر، با هشدار
۴. plannedQuantity × درصد تخصیص
۵. plannedQuantity × درصد فعالیت
۶. unavailable
```

این ترتیب **در این کار تغییر نکرد**. هدف از داده تازه این است که مالی به‌طور طبیعی به
پلهٔ ۲ برسد به‌جای تکیه بر پلهٔ ۳.

در فایل مرجع `Actual Material` روی هر ۷۲۷ تخصیص صفر است — برنامه‌ریز پیشرفت مصالح وارد
نکرده. مالی این را `unavailable` گزارش می‌کند، نه صفر.

## رفتار در برابر خطا

| وضعیت Core | آداپتور |
|---|---|
| هر دو جدول موجود | feed واقعی تخصیص |
| هیچ‌کدام موجود نیست | بازگشت به سطح فعالیت، مقادیر `null` |
| **فقط یکی موجود** | **`CoreSchemaMismatch` — توقف صریح** |

سومی عمدی است. با یک جدول غایب، آداپتور می‌توانست بی‌صدا از درصد فعالیت پاسخ دهد و یک Core
نیمه‌مهاجرت‌یافته دقیقاً شبیه Coreای می‌شد که هرگز مهاجرت نکرده. این تفاوت برای کسی که
مهاجرت را اجرا می‌کند مهم است.

قابلیت در هر درخواست پرسیده می‌شود، نه یک بار: مهاجرت ممکن است بین دو درخواست بنشیند.

## تطبیق

```
۱. تطابق دقیق assignmentExternalId    ← اولویت
۲. بازگشت به کد فعالیت
```

با رسیدن `assignmentExternalId` واقعی، پلهٔ اول کار می‌کند و مسئلهٔ قدیمی حل می‌شود: پیش
از این، دو خط برآورد روی یک فعالیت به یک ردیف می‌رسیدند و **۴۸ ساعت جرثقیل به‌عنوان ۴۸
کیلو میلگرد** گزارش می‌شد.

خط‌های قدیمی بدون `assignmentExternalId` همچنان از پلهٔ دوم می‌آیند. **سخت‌سازی باقی‌مانده:**
وقتی چند تخصیص روی یک فعالیت هست، انتخاب یکی دلبخواهی است. قاعدهٔ درست — بازگشت
منبع‌آگاه، فقط وقتی دقیقاً یک نامزد سازگار وجود دارد و در غیر این صورت «مبهم» — در این کار
پیاده **نشد**، چون تا رسیدن داده واقعی قابل آزمون نیست. مورد بلافاصله پس از E2E.

## وقتی MSP تغییر کند

| تغییر | اثر |
|---|---|
| نام منبع عوض شود | بی‌اثر — هویت UID است |
| مقدار عوض شود | برآورد مالی **بازنویسی نمی‌شود**؛ بازنگری لازم است |
| فعالیت در WBS جابه‌جا شود | گزارش WBS دنبالش می‌رود؛ هویت ثابت |
| منبع افزوده/حذف شود | آزموده نشد — دو نسخهٔ موجود تغییر محتوایی نداشتند |
| فایل «Save As» شود | همهٔ GUIDها بازتولید می‌شوند؛ UIDها می‌مانند |

`estimate_lines.original_quantity` پس از پذیرش **تغییرناپذیر** است — تریگر
`finance_guard_estimate_original` روی PostgreSQL 18 آزموده شده و شلیک می‌کند. تغییر بعدی
مقدار در MSP از راه `estimate_revisions` می‌آید، با دلیل و تاریخ، نه بازنویسی بی‌صدا.
