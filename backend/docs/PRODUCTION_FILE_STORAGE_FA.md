# قرارداد ذخیره فایل برای Production

## وضعیت امروز

`LocalFileStorage` تنها پیاده‌سازی موجود است و در `devhost/ports.py` زندگی می‌کند —
**ماژول توسعه**. بایت‌ها را زیر یک پوشه محلی می‌نویسد.

**در Production قابل دسترسی نیست، و این تصادفی نیست:** `backend/app/` هرگز `devhost` را
import نمی‌کند و یک تست این را تضمین می‌کند. اگر میزبان چیزی برای
`finance_attachment_service` سیم‌کشی نکند، مسیرهای فایل کار نمی‌کنند — و این درست است.

> هیچ Provider بیرونی اختراع نشد. آنچه در ادامه می‌آید **قرارداد** است، نه پیاده‌سازی.

---

## قرارداد

```python
class FileStorage(Protocol):
    async def put(self, metadata, content: bytes) -> str: ...
    async def get(self, organization_id: str, project_id: str, file_id: str) -> bytes: ...
```

فقط دو متد. هر چیز دیگری — Hash، فراداده، اعتبارسنجی، حذف منطقی — کار ماژول مالی است.

### `put(metadata, content) -> stored_name`

| ورودی | |
|---|---|
| `metadata.organization_id` · `metadata.project_id` | برای پارتیشن‌بندی |
| `metadata.stored_name` | نامی **غیرقابل‌حدس** که مالی تولید کرده |
| `content` | بایت‌های خام، از قبل اعتبارسنجی‌شده |

**باید:** بایت‌ها را ماندگار کند و نام ذخیره‌شده را برگرداند.
**نباید:** محتوا را تغییر دهد، فشرده کند، یا نام را بازنویسی کند.

### `get(organization_id, project_id, file_id) -> bytes`

**باید:** فقط فایلی را برگرداند که به همان سازمان **و** همان پروژه تعلق دارد.

> ### 🔴 مرز مجوز
>
> هر دو کلید مستأجر پارامترند و **هر دو باید اعمال شوند**. Storageی که فقط بر اساس
> `file_id` جست‌وجو کند، یک IDOR کامل است: `file_id` قابل حدس نیست ولی «غیرقابل حدس» یک
> کنترل دسترسی نیست.
>
> ماژول مالی پیش از فراخوانی، دامنه را بررسی می‌کند. این لایه دوم است، نه لایه اول — و
> لایه دوم دقیقاً به این دلیل وجود دارد که لایه اول ممکن است یک روز اشتباه کند.

**در نبود فایل:** `FileNotFoundError` بدهید. مالی آن را به `AttachmentStorageUnavailable`
یا ۴۰۴ تبدیل می‌کند.

## آنچه ماژول مالی خودش انجام می‌دهد — Storage تکرارش نکند

| موضوع | جزئیات |
|---|---|
| **اعتبارسنجی نوع** | امضای بایتی خوانده می‌شود، نه فقط پسوند. پسوند، MIME اعلامی و بایت‌ها باید **هر سه** بخوانند |
| نوع‌های مجاز | تصویر: PNG، JPEG، WebP · صوت: MP3، M4A، WAV، OGG |
| **محدودیت حجم** | تصویر ۱۰ مگابایت · صوت ۲۵ مگابایت — در دامنه اعمال می‌شود؛ عبور از آن ۴۱۳ می‌دهد |
| نام امن | مسیر حذف، کاراکترهای کنترلی جایگزین، سقف ۱۲۰ کاراکتر |
| Hash | SHA-256 محتوا، برای تشخیص تکراری |
| فراداده | `finance_attachments` — ۱۶ ستون شامل وضعیت پردازش و حذف منطقی |
| تغییرناپذیری | ردیف فراداده Append-only است |

**بایت‌ها بیرون از ردیف دیتابیس‌اند.** جدول فقط فراداده و کلید ذخیره را نگه می‌دارد.

## حذف

قرارداد **متد حذف ندارد** — عمداً.

ماژول مالی حذف منطقی می‌کند: `deleted_at` را می‌گذارد و ردیف می‌ماند. یک پیوست ممکن است
به فاکتور تأییدشده وصل باشد، و تاریخچه مالی نباید با پاک‌شدن یک فایل ناقص شود.

اگر Storage شما حذف فیزیکی لازم دارد (نگهداری داده، GDPR)، آن یک **فرایند جدا** است که
باید:

1. فقط ردیف‌هایی را هدف بگیرد که `deleted_at` دارند و به هیچ فاکتور تأییدشده‌ای وصل نیستند
2. ردیف فراداده را نگه دارد تا ممیزی بداند چیزی بوده و حذف شده
3. هرگز از مسیر درخواست کاربر اجرا نشود

---

## رفتار در خطا

| وضعیت | پاسخ |
|---|---|
| Storage در دسترس نیست | `503 FINANCE_FILES_UNAVAILABLE` |
| فایل در دامنه نیست | `404` — نه ۴۰۳، تا وجودش تأیید نشود |
| نوع پشتیبانی‌نشده | `415 UNSUPPORTED_MEDIA_TYPE` |
| بزرگ‌تر از حد | `413 FILE_TOO_LARGE` |

**Storage نباید بی‌صدا شکست بخورد.** یک `put` که استثنا نمی‌دهد ولی چیزی ننوشته، ردیف
فراداده‌ای می‌سازد که به هیچ بایتی اشاره نمی‌کند — و این تا روز دانلود دیده نمی‌شود.

---

## چک‌لیست پیاده‌سازی Production

```
□ هر دو کلید مستأجر در مسیر خواندن اعمال می‌شوند
□ put، بایت‌ها را دست‌نخورده می‌نویسد
□ نبودِ فایل، FileNotFoundError می‌دهد
□ خطای Storage استثنا می‌دهد، نه بازگشت خالی
□ Timeout دارد و منتظر بی‌نهایت نمی‌ماند
□ نام ذخیره‌شده‌ای که مالی داد را بازنویسی نمی‌کند
□ در محیط تست، LocalFileStorage استفاده نمی‌شود
```
