# دستورالعمل Migration روی Production

> ## ⛔ قاعده‌ای که هیچ‌وقت نقض نمی‌شود
>
> **Migration روی Production هرگز خودکار نیست.**
>
> راه‌اندازی برنامه Migration اجرا نمی‌کند — این را یک تست قفل کرده. Pipeline استقرار هم
> نباید اجرایش کند. یک انسان باید بعد از دیدن نتیجه دروازه ایمنی، صریحاً تأیید کند.

هیچ رمز یا DSN واقعی در این سند نیست. هرجا `<...>` می‌بینید، مقدار واقعی را از محیط
انتشار بگیرید — نه از اینجا، نه از مخزن.

## ۰. پیش‌بررسی — قبل از هر چیز

```
□ کامیت تأییدشده مشخص است و روی همان ایستاده‌ایم
□ سوئیت بک‌اند روی Python 3.12 سبز است
□ سوئیت فرانت‌اند سبز است
□ alembic heads یک شاخه می‌دهد
□ هیچ Revision جدیدی بدون بازبینی اضافه نشده
□ پنجره زمانی توافق شده و کسی که تأیید می‌کند در دسترس است
```

```bash
cd backend
alembic heads          # باید دقیقاً یک head بدهد
alembic history        # زنجیره 0001..0006 بدون انشعاب
```

## ۱. پشتیبان — قبل از Migration، همیشه

جزئیات در `BACKUP_RESTORE_RUNBOOK_FA.md`.

```
□ پشتیبان گرفته شد
□ حجمش منطقی است (نه صفر، نه خیلی کوچک‌تر از دفعه قبل)
```

> **پشتیبانی که بازیابی‌اش آزموده نشده، پشتیبان نیست.** دست‌کم یک‌بار روی یک دیتابیس
> یک‌بارمصرف بازیابی شود.

## ۲. دروازه ایمنی هدف — اجباری

**پیش از هر دستور Alembic**، این را روی همان اتصالی که Migration استفاده می‌کند اجرا کنید:

```sql
SELECT current_database(),
       inet_server_addr(),
       inet_server_port(),
       version(),
       current_user;
```

نتیجه را با آنچه انتظار دارید **چشمی** مقایسه کنید:

```
□ current_database()  = <نام دیتابیس مورد انتظار>
□ inet_server_addr()  = <آدرس مورد انتظار>
□ inet_server_port()  = <پورت مورد انتظار>
□ version()           = نسخه PostgreSQL مورد انتظار
□ current_user        = نقشی که مجاز به DDL است — نه نقش اجرا
```

**اگر حتی یکی نخواند: متوقف شوید.** دنبال دلیلش نگردید، Migration را اجرا نکنید.

> چرا از خود سرور می‌پرسیم و به DSN اعتماد نمی‌کنیم: یک Tunnel، یک ورودی `pg_hba`، یک
> Port-forward قدیمی یا یک اشتباه تایپی همگی می‌توانند یک DSN را جای دیگری ببرند. DSN یک
> **ادعا** است؛ `current_database()` یک **پاسخ**.

## ۳. تأیید انسانی — نقطه توقف

بعد از دیدن خروجی دروازه، شخصِ تأییدکننده باید صریحاً بگوید ادامه دهید.

```
□ خروجی دروازه به تأییدکننده نشان داده شد
□ تأیید صریح گرفته شد
□ نام تأییدکننده و زمان ثبت شد
```

**اگر این مرحله در یک اسکریپت خودکار شد، دیگر دروازه نیست.**

## ۴. اجرای Migration

```bash
cd backend
export FINANCE_MIGRATION_DSN="<owner-dsn>"     # فقط در همین Shell
alembic upgrade head
```

**نکات:**

- `FINANCE_MIGRATION_DSN` نقش **Owner** است. نقش اجرا عمداً حق `CREATE` ندارد
- این متغیر را در فایل نگذارید و در تاریخچه Shell نگه ندارید
- خروجی را ذخیره کنید

**برای دیدن SQL بدون اجرا** (توصیه‌شده برای بازبینی قبلی):

```bash
alembic upgrade head --sql > /tmp/planned.sql
```

هر شش Revision در حالت Offline هم کار می‌کنند.

## ۵. اعتبارسنجی — بلافاصله بعد

```sql
SELECT version_num FROM finance_alembic_version;      -- باید 0006 باشد

SELECT count(*) FROM information_schema.tables
 WHERE table_schema='public' AND table_name LIKE 'finance%'
    OR table_name IN ('estimate_lines','estimate_revisions','price_versions',
                      'unit_conversions','progress_snapshot_refs','progress_overrides',
                      'invoices','invoice_lines','report_snapshots','extraction_drafts');

SELECT count(*) FROM pg_trigger t JOIN pg_class k ON k.oid=t.tgrelid
 WHERE NOT t.tgisinternal AND k.relnamespace='public'::regnamespace;   -- ۱۰ تریگر
```

```
□ finance_alembic_version = 0006
□ ۱۵ جدول مالی موجودند
□ ۱۰ تریگر تغییرناپذیری موجودند
□ جدول عمومی alembic_version ساخته نشده
□ داده موجود دست‌نخورده است
```

> **`finance_alembic_version` عمداً این نام را دارد، نه `alembic_version`.** دیتابیس BAMBO
> مشترک است و ماژول مالی نباید نام عمومی را برای خودش بردارد.

## ۶. تصمیم بازگشت

جزئیات در `ROLLBACK_RUNBOOK_FA.md`.

**در همین لحظه تصمیم بگیرید، نه بعداً:**

| نشانه | اقدام |
|---|---|
| Migration خطا داد و تراکنش برگشت | ادامه ندهید؛ علت را پیدا کنید. Schema دست‌نخورده است |
| Migration موفق ولی اعتبارسنجی رد شد | **دیتابیس را Downgrade نکنید.** اول بفهمید چه چیزی نمی‌خواند |
| برنامه بعد از استقرار خطا می‌دهد | برنامه را برگردانید. Downgrade دیتابیس معمولاً لازم نیست |

> **بازگشت برنامه ≠ بازگشت دیتابیس.** این دو تصمیم جدا هستند و اغلب فقط اولی لازم است.

## آنچه این دستورالعمل هرگز نمی‌گوید انجام دهید

| ممنوع | چرا |
|---|---|
| `alembic downgrade` روی Production بدون تصمیم جداگانه | تاریخچه مالی وارد‌شده را از دست می‌دهید |
| `alembic stamp` برای «درست‌کردن» وضعیت | نسخه را عوض می‌کند بدون اینکه Schema را عوض کند — بدترین حالت ممکن |
| اجرای Migration از مسیر راه‌اندازی برنامه | اجرای یک پروسه، رضایت به تغییر Schema نیست |
| ساخت جدول با SQL دستی | Alembic تنها مرجع Schema است |
| Seed یا داده نمایشی روی Production | هرگز، تحت هیچ شرطی |
| ساخت مجوز در جدول `permissions` هسته | RBAC مال هسته است |
