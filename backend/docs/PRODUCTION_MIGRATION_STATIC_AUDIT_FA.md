# ممیزی ایستای مهاجرت‌های مالی — پیش از نصب روی تولید

**تاریخ:** ۱۴۰۵/۰۶/۰۵ (2026-08-27) · **Commit:** `dae451f` · **دامنه:** `0001` → `0006`

**هیچ اتصالی به تولید برقرار نشد.** این ممیزی فقط فایل می‌خواند. `192.168.100.200` لمس نشد،
اعتبارنامه‌ای خوانده یا خواسته نشد، و SQL تولیدشده روی هیچ دیتابیسی اجرا نشد.

---

## روش

هر عملیات این شش بازنگری از راه `op.execute` با یک رشته SQL انجام می‌شود، و رشته‌ها ثابت‌های
سطح‌ماژول‌اند (`op.execute(DDL(UPGRADE_SQL))`). ممیزی، Python را با `ast` تجزیه می‌کند، نام‌ها
را به ثابت‌هایشان می‌رساند، و **هر آرگومانی را که به‌طور ایستا قابل دانستن نباشد گزارش می‌کند
نه اینکه رد شود** — یک دستور محاسبه‌شده دقیقاً همان چیزی است که ممیزی ایستا نباید از آن بگذرد.

نتیجه: **۰ آرگومان غیرِ ثابت.** همه SQL پیش از اجرا خوانده شد.

لایه دوم: تولید SQL آفلاین با `alembic upgrade head --sql` (بدون اتصال به دیتابیس)، ۵۴۵ خط،
که مستقل از تجزیه منبع بازرسی شد.

## مدل تراکنش

**`FULLY_TRANSACTIONAL`**

`env.py` هر دو مسیر آنلاین و آفلاین را داخل `context.begin_transaction()` می‌برد. در هیچ
بازنگری‌ای `CONCURRENTLY`، `autocommit` یا تغییر `isolation_level` نیست. یعنی اگر مهاجرت
شکست بخورد، چیزی نیمه‌کاره جا نمی‌ماند.

## نمایه قفل

**`NEW_OBJECT_ONLY`**

هیچ بازنگری‌ای به شیء از پیش موجودِ Core قفل نمی‌زند، چون هیچ‌کدام نامش را هم نمی‌برند.
قفل‌ها روی جدول‌هایی‌اند که همان مهاجرت لحظاتی پیش ساخته.

مسیر `downgrade` این بازنگری، اگر نتواند `NOT NULL` بازنگری ۰۰۰۵ را برگرداند، عمداً امتناع

اثری ندارد** — این فاز هرگز downgrade اجرا نمی‌کند.

## دو یافته که پیش از نصب باید دیده شوند

### ۱ — MEDIUM: مقصد schema به `search_path` وابسته است

هیچ دستوری در این شش بازنگری با `public.` مقید نشده، و نه `env.py` و نه هیچ مهاجرتی
`SET search_path` نمی‌زند (`version_table_schema` هم تنظیم نشده). یعنی اشیاء مالی در **نخستین
schema قابل‌نوشتنِ `search_path`** ساخته می‌شوند.

`search_path` تولید — که در preflight فقط‌خواندنیِ نوبت پیش از خودِ سرور خوانده شد — این است:

```
"$user", public
```

اگر schemaیی هم‌نام نقش مهاجرت وجود داشته باشد، جدول‌های مالی **در آن** ساخته می‌شوند نه در
`public`، و مهاجرت با موفقیت تمام می‌شود بی‌آنکه چیزی هشدار دهد.

**راه‌حل بدون تغییر کد:** در preflight، پیش از `alembic upgrade`، این را بپرسید:

```sql
SELECT count(*) FROM pg_namespace WHERE nspname = current_user;   -- باید ۰ باشد
```

اگر ۰ بود، `"$user"` به هیچ schemaیی نمی‌رسد و `public` مقصد می‌شود. اگر ۰ نبود، **بایستید** —
این تصمیمِ معماری استقرار است، نه چیزی که مهاجرت باید بی‌سر و صدا حل کند.

`env.py` را برای این تغییر ندادم: قرارداد تأییدشده‌اش باید دست‌نخورده بماند، و یک سنجه در
preflight همان تضمین را بدون تغییر کدِ اعتبارسنجی‌شده می‌دهد.

### ۲ — LOW: مسیر مهاجرت به بسته `devhost` وابسته است

`alembic/env.py` این را import می‌کند:

```python
from devhost.environment import MissingConfiguration, migration_url
```

پس محیط مهاجرتِ تولید باید `devhost/environment.py` را همراه داشته باشد. (بسته قابل‌استقرار
`app/` هرگز `devhost` را import نمی‌کند — این فقط درباره مسیر مهاجرت است.)

نکته دوم: `migration_url()` تنها `FINANCE_MIGRATION_DSN` را می‌خواند — بدون fallback به
`DATABASE_URL`، بدون fallback به localhost — ولی `setting()` اگر متغیر محیطی نبود، سراغ فایل
`backend/.env` می‌رود. **همین حالا `backend/.env` وجود ندارد**، پس امروز مسئله‌ای نیست؛ ولی
پیش از مهاجرت تولید باید دوباره تأیید شود که فایلی آنجا نیست که مقصد را بی‌صدا عوض کند.

## حکم

```
SAFE_FOR_CONTROLLED_PRODUCTION_SCHEMA_INSTALL
```

با دو شرط ورودی از بند بالا: `search_path` باید به `public` برسد، و `backend/.env` نباید
مقصد را بپوشاند.

این حکم فقط درباره **خودِ مهاجرت‌ها**ست. نصب همچنان مسدود است، به دلیلی بیرون از این ممیزی:
نقش مهاجرتی که در preflight نوبت پیش آزموده شد، روی هر ۴۷ جدول Core حق `INSERT`/`UPDATE`/
`DELETE` دارد (از راه اعطا به `PUBLIC`) و `CREATE` روی `public` ندارد. یعنی کاری را که باید
بتواند نمی‌تواند، و کاری را که نباید بتواند می‌تواند. آن، تصمیم تیم Core است.
