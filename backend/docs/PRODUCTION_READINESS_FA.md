## تحلیل سازگاری PostgreSQL 18

Production روی ۱۸٫x است؛ محلی ۱۶٫۱۵. کل SQL شش Revision و همه Queryهای زمان اجرا بررسی شد.

| مورد | استفاده | ارزیابی |
|---|---|---|
| `numeric(p,s)` | ۲۳ ستون | بدون تغییر در ۱۸ |
| تولید UUID | **هیچ** — برنامه تولید می‌کند | بدون وابستگی به pgcrypto یا `uuidv7()` |
| Index جزئی | ۳ مورد | بدون تغییر |
| قید CHECK | ۴۶ مورد | بدون تغییر |
| تریگر + plpgsql | ۱۰ تریگر، ۳ تابع | بدون تغییر |
| `::regclass` | ۲ مورد (فقط در 0006) | بدون تغییر |
| `jsonb` | ۱۵ مورد | بدون تغییر |
| `timestamptz` | ۲۴ مورد | بدون تغییر |
| `ON CONFLICT` | ۲ مورد در زمان اجرا | بدون تغییر |
| قفل Advisory | `pg_advisory_xact_lock(hashtext(...))` | بدون تغییر |
| `SERIAL` / IDENTITY | **هیچ** در جدول‌های مالی | — |
| `information_schema` / `pg_catalog` | فقط در ابزار دمو | مسیر Production نیست |
| کلمات رزرو | `source` به‌عنوان نام ستون | در PG رزرونشده است؛ روی ۱۶ کار می‌کند |

**ارزیابی: ریسک پایین.** هیچ ساختاری استفاده نشده که ۱۷ یا ۱۸ تغییرش داده باشند. تغییرات
بزرگ ۱۸ — I/O ناهم‌زمان، `uuidv7()`، ستون‌های تولیدی مجازی، OAuth — هیچ‌کدام در این مسیر
نیستند.

> **ولی این تحلیل است، نه اجرا.** شکاف تا وقتی یک PostgreSQL 18 یک‌بارمصرف چرخه
> `base → 0006 → base → 0006` را نبیند، باز است.
>
> **یک PostgreSQL 17.6 روی `127.0.0.1:5433` موجود است** (زیر `E:\bamboo\_local\pgsql`) ولی
> رمز می‌خواهد. اجرای همان چرخه روی ۱۷ بیشتر فاصله ۱۶→۱۸ را پوشش می‌دهد. اگر DSN فقط‌محلی‌اش
> را بدهید، انجام می‌شود.

به ترتیب وابستگی:
