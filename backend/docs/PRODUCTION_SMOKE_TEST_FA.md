# بخش الف — فقط‌خواندنی

هیچ‌کدام از این‌ها چیزی نمی‌نویسند. اگر یکی رد شد، **قبل از رفتن به بخش ب متوقف شوید**.

## الف-۱. راه‌اندازی و سلامت

```
□ برنامه بالا آمده و پاسخ می‌دهد
□ لاگ راه‌اندازی خطا ندارد
□ لاگ نمی‌گوید Migration اجرا شده  ← اگر گفت، ایراد پیکربندی است
□ لاگ نمی‌گوید داده نمایشی بارگذاری شده
```

> دو ردیف آخر مهم‌اند: راه‌اندازی نباید هیچ‌کدام را انجام دهد. اگر لاگ خلافش را گفت،
> محیط اشتباه پیکربندی شده و باید متوقف شوید.

## الف-۲. هویت و دامنه

```
□ درخواست بدون Session ← رد می‌شود
□ درخواست با Session معتبر ← AuthContext ساخته می‌شود
□ کاربری خارج از سازمان ← ۴۰۳
□ کاربری خارج از پروژه ← ۴۰۳
□ پروژه‌ای در سازمان دیگر ← ۴۰۳، نه داده
```

## الف-۳. خواندن مالی

هر کدام باید **۲۰۰** بدهند و داده همان پروژه را برگردانند:

```
□ GET  .../finance/settings
□ GET  .../finance/settings/revisions
□ GET  .../finance/resources
□ GET  .../finance/unit-registry
□ GET  .../finance/activities

□ GET  .../finance/prices/current?asOf=<date>
□ GET  .../finance/price-history
□ GET  .../finance/unit-conversions
□ GET  .../finance/invoices
□ GET  .../finance/progress-snapshots
□ GET  .../finance/summary
□ GET  .../finance/audit-events
```

## الف-۴. گزارش

```
□ GET  .../finance/reports/live?reportingDate=<date>     → ۲۰۰
□ GET  .../finance/reports/live/variances                 → ۲۰۰
□ GET  .../finance/reports/monthly?reportingDate=<date>   → ۲۰۰
□ GET  .../finance/report-snapshots                       → ۲۰۰
```

**در پاسخ گزارش زنده این‌ها را بخوانید:**

```
□ calculationStatus  — complete یا incomplete؟
□ warnings           — کدام‌ها و چند تا؟
□ progressQuality    — چند خط اندازه‌گیری‌شده، چند تا unavailable؟
```

> ### `incomplete` لزوماً خرابی نیست
>
> اگر خوراک پیشرفت مقدار اجراشده ندارد، گزارش صادقانه `incomplete` می‌دهد و سنجه‌های
> وابسته `null` برمی‌گردند. **این درست است** — و امروز حالت مورد انتظار است، چون هسته
> منبع مقدار اجراشده ندارد. جزئیات در `PROGRESS_INTEGRATION_GAP_FA.md`.
>
> آنچه **نباید** ببینید: عدد صفر به‌جای مقدار غایب.

## الف-۵. پیوست

```
□ GET  .../finance/files            → ۲۰۰
□ GET  .../finance/files/<id>       → ۲۰۰ برای فایل همین پروژه
□ GET  .../finance/files/<id>       → ۴۰۴ برای فایل پروژه دیگر  ← نه ۴۰۳
```

> ۴۰۴ نه ۴۰۳: پاسخ «ممنوع» تأیید می‌کند که آن فایل وجود دارد.

## الف-۶. مرزی که باید بسته بماند

```
□ POST .../finance/report-snapshots   → ۴۰۳
```

**این باید رد شود** تا وقتی `finance_report.issue` در هسته ساخته شود. اگر ۲۰۰ داد، یعنی
مجوز به یک کد ضعیف‌تر نگاشت شده — که دقیقاً همان چیزی است که رد شد.
جزئیات در `CORE_PERMISSION_REQUIREMENTS_FA.md`.

```
□ رابط کاربری هم دکمه «ثبت گزارش دوره‌ای» را نشان نمی‌دهد
```

# بخش ب — نوشتن کنترل‌شده

> ## ⛔ فقط بعد از اینکه کل بخش الف سبز شد و استقرار صریحاً تأیید شد
>
> این بررسی‌ها **داده واقعی می‌سازند**. روی پروژه‌ای اجرا کنید که برایش توافق شده، و هر
> رکوردی که ساختید را ثبت کنید.

## ب-۱. یک ویرایش قابل بازگشت

```
□ PATCH .../finance/settings با زیربنای جدید  → ۲۰۰
□ GET   .../finance/settings                  → مقدار جدید
□ GET   .../finance/settings/revisions        → ردیف قبلی هنوز آنجاست
```

> نسخه قبلی **باید** بماند. اگر جایگزین شد، تغییرناپذیری کار نمی‌کند و باید متوقف شوید.

## ب-۲. چرخه فاکتور

```
□ POST  .../finance/invoices                     → پیش‌نویس ساخته شد
□ PATCH .../finance/invoices/<id>                → ویرایش پیش‌نویس کار می‌کند
□ POST  .../finance/invoices/<id>/confirm        → تأیید شد
□ PATCH .../finance/invoices/<id>                → حالا باید رد شود
□ همان درخواست confirm دوباره                    → همان نتیجه، نه فاکتور دوم
```

ردیف چهارم و پنجم مهم‌ترند: فاکتور تأییدشده تغییرناپذیر است، و تأیید تکراری نباید هزینه را
دوباره ثبت کند.

## ب-۳. مسیرهایی که هنوز نباید کار کنند

```
□ POST .../finance/report-snapshots          → ۴۰۳ (مجوز در هسته نیست)
□ POST .../finance/files/<id>/extractions    → ۵۰۳ (Provider پیکربندی نشده)
```

هر دو **انتظار می‌رود رد شوند**. اگر یکی موفق شد، چیزی پیکربندی شده که نباید.

## ب-۴. تمیزکاری

```
□ هر رکوردی که در بخش ب ساخته شد ثبت شد
□ فاکتورهای آزمایشی باطل شدند، نه حذف — حذف امکان ندارد و نباید داشته باشد
□ تیم مالی از رکوردهای آزمایشی خبر دارد
```

> **هیچ‌چیزی که در بخش ب ساخته شد قابل حذف نیست.** تاریخچه مالی Append-only است. برای همین
> بخش ب فقط با تأیید صریح اجرا می‌شود.
