# شکاف پیشرفت — چرا مقدار اجراشده از هسته درنمی‌آید

## خلاصه در یک جمله

هسته می‌گوید یک Task **۳۰٪ انجام شده**؛ نمی‌گوید آن ۳۰٪ **چند کیلوگرم میلگرد** است. و مالی
برای تبدیل پیشرفت به پول، دقیقاً به دومی نیاز دارد.

---

## هسته امروز چه می‌دهد

| جدول | چه دارد | برای مالی قابل استفاده؟ |
|---|---|---|
| `msp_snapshots` | هویت bigint، نوع، زنجیره `previous_snapshot_id`، تاریخ وضعیت شمسی | ✅ کامل |
| `msp_file_versions` | فایل مبدأ، شماره نسخه، تاریخ آپلود | ✅ کامل |
| `msp_tasks` | نام، WBS، `outline_number`، تاریخ‌ها، `percent_complete`، `percent_work_complete`، `physical_percent_complete` | ⚠ فقط درصد |

## هسته چه ندارد

```
هیچ جدول تخصیص منبع (assignment)         ← وجود ندارد
msp_tasks: ستون منبع                     ← وجود ندارد
msp_tasks: ستون واحد                     ← وجود ندارد
msp_tasks: ستون مقدار برنامه‌ای یا اجراشده ← وجود ندارد
```

**هر ۳۰ ستون `msp_tasks` بررسی شد.** هیچ‌کدام مقدار فیزیکی نیست.

---

## مالی چه لازم دارد

برای هر ردیف خوراک پیشرفت:

```
assignmentExternalId    شناسه پایدار تخصیص
resourceExternalId      کدام منبع
unit                    واحد همان منبع
plannedQuantity         مقدار برنامه‌ای
actualQuantity          مقدار اجراشده     ← این عدد، پول می‌سازد
task { activityCode, wbsCode, taskProgressPercent, ... }
```

فقط `actualQuantity` است که در `executed × قیمت روز` ضرب می‌شود.

---

## آنچه هرگز نباید استنتاج شود

سه راه میان‌بر بررسی و **رد** شدند. هر سه عدد تولید می‌کنند و هر سه دروغ می‌گویند:

| میان‌بر | چرا رد شد |
|---|---|
| `درصد Task × مقدار برآورد` | عددی می‌سازد که **همیشه با برآورد می‌خواند**. یعنی سنجه‌ای که هرگز نمی‌تواند مشکلی را لو بدهد — بدترین نوع عدد در یک داشبورد مالی |
| `percent_work_complete` به‌جای درصد مقدار | تلاش را اندازه می‌گیرد، نه سهمی از یک مقدار فیزیکی. همان خلط «ساعت‌کار به‌جای مقدار» که `domain/progress.py` برای توقفش بازنویسی شد |
| ساختن `assignmentExternalId` مصنوعی | ارتباطی جعل می‌کند که هسته ادعایش را ندارد. بعد از آن، هیچ‌چیز نمی‌تواند تشخیص دهد کدام تطبیق واقعی بوده |
| استنتاج از `Duration` | مدت زمان، مقدار نیست. یک Task ممکن است دو برابر طول بکشد و نصف مقدار را اجرا کرده باشد |

## قاعده‌ای که حفظ می‌شود

> **مقدار اجراشده‌ی غایب ≠ صفر.**

وقتی خوراک مقداری ندارد، ماژول مالی آن خط را `unavailable` با هشدار `PROGRESS_MISSING`
نشان می‌دهد — نه صفر. تفاوت مهم است: صفر یعنی «اندازه گرفتیم و هیچ نبود»؛ `unavailable`
یعنی «اندازه‌ای در دست نیست».

`calculationStatus` هم `incomplete` می‌شود و سنجه‌های وابسته `null` برمی‌گردند، نه عددی که
کمتر از واقعیت است.

Adapter هسته (`coreint/progress.py`) همین کار را می‌کند: ردیف سطح-Task با تمام فیلدهای
مقدار خالی. تست‌ها این را قفل کرده‌اند.

## رابط پیشنهادی برای ماژول پیشرفت میزبان

مقادیر سطح-تخصیص باید از **جایی بیاید که منتشرشان می‌کند** — ماژول پیشرفت میزبان که فایل
MPP را می‌خواند و تخصیص منابع را استخراج می‌کند.

```python
async def get_snapshot(organization_id, project_id, snapshot_id) -> {
    "snapshot": {
        "organizationId", "projectId",
        "progressSnapshotId",   # همان شناسه‌ای که با آن پرسیده شده
        "hostSnapshotId",       # bigint هسته
        "hostFileVersionId",    # bigint هسته
        "reportingDate",        # ISO — ترجیحاً از تاریخ وضعیت برنامه‌ریز
        "status",               # ready | superseded
        "sourceType",           # mpp | host_feed | synthetic
        "importedBy", "importedAt",
    },
    "assignments": [ ... ],     # با فیلدهای بالا
}

async def current_snapshot(organization_id, project_id, as_of) -> همان شکل | None
```

**سه قاعده که پیاده‌سازی باید رعایت کند:**

1. با همان شناسه‌ای جواب بدهد که با آن پرسیده شده
2. در نبود Snapshot، `None` — نه Header خالی
3. مقداری که ندارد را نسازد؛ `null` بگذارد و بگذارد مالی هشدار بدهد

## یک نقص باز، جدا از این شکاف

وقتی تطبیق به کد فعالیت برمی‌گردد (چون تخصیصی در کار نیست)، **دو خط برآورد روی یک فعالیت
با یک ردیف Task تطبیق می‌خورند**.

در حالت فعلی زیانی ندارد: بدون مقدار، هر دو `unavailable` می‌شوند. ولی Providerی که مقدار
سطح-Task بدهد، به هر دو خط یک عدد می‌دهد بدون توجه به منبع.

این در داده نمایشی واقعاً رخ داد: یک اصلاح دستی که برای قالب‌بندی ثبت شده بود، روی
آرماتوربندی هم اعمال شد و پیش‌بینی نیروی انسانی ۲٫۱ میلیارد تومان بالا آمد. در Seed با
جداکردن فعالیت‌ها حل شد — که مدل‌سازی درست‌تری هم هست — ولی **رفتار قاعده وقتی فعالیت
واقعاً مشترک است، همچنان یک تصمیم باز است.**
