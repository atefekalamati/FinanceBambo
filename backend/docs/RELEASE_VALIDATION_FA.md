| همان نام، محتوای عوض‌شده | بایت‌ها تشخیص داده شد و `MPP_CURRENCY_UNRESOLVED` **رد کرد** — هر دو نسخهٔ قبلی، ۷۸۹+۷۸۹ ردیف، ۸۳۸ خط برآورد و نسخهٔ فعال دست‌نخورده |
| دو sync `unchanged` هم‌زمان | هر دو `unchanged`، شمارش‌ها ثابت |
| دو `refresh` هم‌زمان (حذف + بازنویسی) | هر دو `refreshed`، همان ۷۸۹ ردیف، `stated == actual` — قفل ردیفیِ Postgres سریالی‌شان می‌کند |
| فایل جدیدِ **پذیرفتنی** هم‌زمان | **BLOCKED** — دروازهٔ ارز فقط دو sha تأییدشده را می‌پذیرد و افزودن sha یک تصمیم تجاری است |

سطر سوم همان چیزی است که خواسته شده بود: import مبهم‌ازنظر‌ارز وضعیت معتبر قبلی را حفظ می‌کند.

### ۲) روال پشتیبانی‌شدهٔ اصلاح ledger — جدید

`finance_alembic_version` روی دیتابیس کاری `0013` است در حالی که ساختارهای `0014`–`0016`

پس `backend/scripts/reconcile_ledger.py` اضافه شد: روال مروری برای دیتابیسی که مهم است.

**آنچه اثبات می‌کند، پیش از آنکه چیزی بنویسد:**

1. بازهٔ نسخه‌ها را از ledger تا head مخزن خودش می‌سازد (`0013 → 0014, 0015, 0016`).
2. آن بازه را برای **data migration** می‌کاود. اگر یکی پیدا شود امتناع می‌کند: مقایسهٔ
   schema هیچ چیز دربارهٔ یک backfill اجرانشده نمی‌گوید. برای این بازه: **هیچ‌کدام DML
   ندارند** — همه DDL خالص‌اند.
3. فقط جدول‌هایی را مقایسه می‌کند که همان نسخه‌ها لمس می‌کنند
   (`finance_mpp_source_versions`، `finance_mpp_rows`، `estimate_line_source_completions`).
4. برای هر جدول: **ستون‌ها** (با نوع، nullability، default، identity، generated)،
   **قیدها**، **ایندکس‌ها** و **تریگرها همراه بدنهٔ تابعشان** — با همان کوئری‌های کاتالوگ
   ابزار قبلی، نه یک کپی تازه. **وجودِ ستون به‌تنهایی معیار نیست.**
5. قفل: `SELECT … FOR UPDATE` روی ردیف ledger و
   `LOCK TABLE … IN SHARE ROW EXCLUSIVE MODE` روی آن جدول‌ها — همان قراردادی که `0009` دارد.
6. اثرانگشت محتوای **۷۳ جدول کاری** قبل و بعد؛ اگر تغییر کند، rollback.
7. فقط با `--apply` **و** `--confirm-database <نام دقیق>` می‌نویسد، و تنها یک ستون:
   `finance_alembic_version.version_num`.
8. رسید JSON چاپ می‌کند: هدف، بازه، جدول‌های مقایسه‌شده، و دقیقاً چه چیزی تغییر کرد.

**بازیابی روی یک دیتابیس تازه، سپس تغییر DSN میزبان — هرگز بازنویسی روی دیتابیس کاری.**

### ۳) نصب Core — درخواست دقیق از تیم میزبان

▫ قرارداد از DDL استخراج شده بود و ✅ در همین مرحله دوباره از مخزن خوانده شد: ۱۶ نسخه،
زنجیرهٔ تک‌شاخه، head = `0016`.

**ابزار نصب معتبر Core در سورس‌های مجاز این پروژه وجود ندارد.**
`scripts/demo/core_mirror.sql` سربرگ خودش می‌گوید آینهٔ دموی محلی است و هرگز روی دیتابیس
Core اعمال نمی‌شود؛ به‌عنوان نصب‌کننده استفاده نشد. **تمرین نصب با آینه، اثبات آمادگی نصب
واقعی روی میزبان نیست.** پس نصب سرتاسری **مسدود** است.

**درخواست واحد از تیم میزبان:**

1. **بستهٔ مهاجرت Core** — نام بسته و نسخه/revision دقیقی که این‌ها را می‌سازد؛ **یا**
   قرارداد دیتابیس مشترک BAMBO که Core آن‌ها را در آن نگه می‌دارد.
2. **schema لازم:**
   - `msp_tasks` با ستون `id` از نوع `bigint` (کلید خارجی `0009`:
     `finance_task_resource_map.task_id → msp_tasks(id) ON DELETE CASCADE`)
   - `msp_snapshots` (تریگر دامنهٔ `0009` برای یافتن پروژهٔ یک task به آن join می‌زند)
   - `msp_resources` و `msp_resource_assignments` لازم **نیستند** — `0007` خودش می‌سازدشان
3. **دسترسی:** `GRANT REFERENCES ON msp_tasks TO <نقش مهاجرت>` در محیطی که نقش محدود است.
4. **ترتیب نصب:** schema هستهٔ Core → `alembic upgrade head`. روی دیتابیس خالی، ارتقا تا
   `0008` می‌رود و روی `0009` با پیام خودتوضیح می‌ایستد؛ ارتقا اتمیک است و چیزی نیمه‌کاره
   باقی نمی‌گذارد.
5. **آیا دیتابیس مشترک الزامی است؟** برای `0009` بله — یا Core در همان دیتابیس باشد، یا
   یک `msp_tasks` سازگار از پیش وجود داشته باشد. Finance مالک آن schema نیست و نباید بشود.
6. **دستور اعتبارسنجی و خروجی مورد انتظار:**

```
python -m scripts.install_preflight --dsn postgresql://<user>@<host>:<port>/<database>
```

خروجی مورد انتظار روی محیطی که آماده است: `Every prerequisite is present.` و کد خروج `0`.
اگر آماده نیست، کد خروج `1` و نام دقیق کمبود به‌همراه گام بعدی. `2` یعنی دیتابیس در دسترس
نبود. این ابزار **فقط می‌خواند** و روی هر دیتابیسی بی‌خطر است.

### ۵) تاریخ اثر تجاری برآوردها — تصمیم کسب‌وکار، چیزی پیاده نشد

▫ فیلترها و قواعد موجود بازبینی شدند و ✅ در همین مرحله فیلدهای تاریخی واقعی شمرده شدند:

| کلاس رکورد | فیلدهای تاریخ موجود | تاریخ اثر تجاری دارد؟ |
|---|---|---|
| قلم برآورد (اصل) | `created_at`، `deleted_at` | **ندارد** — فقط زمان نوشتن ردیف |
| بازنگری برآورد | `created_at` | **ندارد** |
| تکمیل اصلِ جاافتاده | `completed_at` | **ندارد** — زمان نوشتن مقدار |
| نسخهٔ منبع MPP | `imported_at`، `reporting_date` | `reporting_date` = Status Date **فایل**، نه تاریخ تأیید برآورد |
| نسخهٔ قیمت | **`effective_from`** | **دارد** ✅ |
| تنظیمات پروژه | **`effective_from`** | **دارد** ✅ |

یعنی قرارداد `effective_from` در همین کد **وجود دارد** و درست کار می‌کند — فقط روی
برآوردها نیست، و هیچ منبعی آن را نمی‌گوید.

**مثال مشخص (Assignment 9703، دادهٔ واقعی):**

```
ردیف ساخته شد        2026-09-07
مقدار اصل نوشته شد   2026-09-09   (تکمیل، چون original_* هر دو NULL بودند)
نسخهٔ مورد استناد    afe50159، imported 2026-09-05، Status Date = NULL
نسخهٔ فعال           bf456698، Status Date = 2025-10-02
```

چهار تاریخِ ممکن، و هیچ شاهدی که کدام «تاریخ اثر» است. نکتهٔ تعیین‌کننده: نسخه‌ای که این
قلم به آن استناد می‌کند **هیچ Status Date ندارد**، پس گزینهٔ «تاریخ فایل» برای همین قلم
حتی در دسترس نیست.

**اثر هر گزینه بر تعداد اقلام در دامنهٔ یک گزارش زنده:**

| قاعده | ۲۰۲۵‑۱۰‑۰۲ | ۲۰۲۶‑۰۹‑۰۵ | ۲۰۲۶‑۰۹‑۰۷ | ۲۰۲۶‑۰۹‑۰۹ |
|---|---|---|---|---|
| A `created_at` (قاعدهٔ امروز) | ۰ | ۱۲۰ | ۸۳۵ | ۸۳۵ |
| B تاریخ نوشتن مقدار (`completed_at`) | ۰ | ۱۲۰ | ۵۴۶ | ۸۳۵ |
| C Status Date نسخهٔ مورد استناد | ۰ | ۱۲۰ | ۸۳۵ | ۸۳۵ |
| D Status Date نسخهٔ فعال | **۸۳۵** | ۸۳۵ | ۸۳۵ | ۸۳۵ |

خواندن این جدول:

- **A و C یکسان‌اند**، چون نسخه‌های مورد استناد Status Date ندارند. پس «از تاریخ فایل
  استفاده کنیم» برای دادهٔ موجود **هیچ چیز را تغییر نمی‌دهد** — که خودش نشان می‌دهد شاهد
  گمشده این نیست.
- **B سخت‌گیرانه‌تر** است: ۲۸۹ قلم را تا روزی که مقدارشان نوشته شد عقب می‌اندازد.
- **D تاریخ را صاف می‌کند**: گزارش ۲۰۲۵‑۱۰‑۰۲ ادعا می‌کند پروژه از همان زمان کل برآوردش را
  داشته، و با **۱۶ گزارش منجمد** موجود در `2026-09-05` و `2026-09-07` (که با قاعدهٔ A
  محاسبه شده‌اند و در ۰۹‑۰۵ عدد ۱۲۰ را نشان می‌دهند) تناقض پیدا می‌کند. گزارش منجمد
  بازنویسی نمی‌شود، پس نتیجه دو پاسخ متفاوت برای یک تاریخ است.

**تصمیم لازم:** برای ۸۳۵ قلم موجود، «تاریخ اثر تجاری» کدام است — و منبع معتبرش چیست؟
همچنین: بازنگری از تاریخ ثبتش معتبر است یا از تاریخی که کاربر اعلام می‌کند؟ و «اصلاح یک
اشتباه» که باید در گزارش دورهٔ گذشته هم دیده شود، چگونه از «تغییر واقعاً بعدی» جدا می‌شود؟

**پیشنهاد — و این فقط یک پیشنهاد است، نه تصمیم:** یک ستون `effective_from` به
`estimate_lines` و `estimate_revisions` اضافه شود، دقیقاً به همان الگوی `price_versions`
که در این کد جا افتاده است، و **فقط جایی پر شود که شاهد دارد**؛ هر جا ندارد `NULL` بماند و
همان رفتار «نامعلوم» فعلی ادامه یابد. این یک ستون است، نه یک سیستم زمانی جدید. ولی تا وقتی
پاسخ سه پرسش بالا معلوم نشود، پر کردن آن ستون حدس زدن است.

**تا آن زمان چیزی تغییر نکرد:** هیچ رکوردی عقب‌تاریخ نشد، هیچ فیلتری حذف نشد، و رفتار
صریح «ناقص/نامعلوم» دست‌نخورده ماند.

### Migration — هدف واقعی، گاردها، و پیش‌نیاز

- **هدف واقعی از خودِ مخزن خوانده شد، نه از ادعا**: ۱۶ revision روی دیسک، زنجیرهٔ تک‌شاخهٔ
  `0001 → … → 0016`، و `heads = ['0016']`. پس 0016 هدف درست است.
- **0014 تا 0016 دقیقاً همان سه جدولی را تغییر می‌دهند که اسکریپت مقایسه می‌کند**:
  0014 ستون `reporting_date` را به `finance_mpp_source_versions` می‌افزاید؛ 0015 ستون‌های

  `estimate_line_source_completions`. هیچ‌کدام جدولی به نام `finance_mpp_assignment_facts`
  نمی‌سازد — نام فایل، نام قابلیت است نه نام جدول. (تصحیح یک برداشت نادرست پیشین.)
- **گاردهای اسکریپت با اجرا آزموده شدند، نه با مطالعهٔ کد:**

1. **مرجع معتبر تاریخ اثر برآورد اولیه** — امروز فیلتر `created_at` است، یعنی «کِی ثبت شد»

   دیده شود؛ یک تغییر واقعی نباید. امروز هیچ فیلدی این دو را از هم جدا نمی‌کند.
