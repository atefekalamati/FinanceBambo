# دستورالعمل بازگشت

> ## قاعده‌ای که همه‌چیز از آن شروع می‌شود
>
> **بازگشت برنامه ≠ بازگشت دیتابیس.**
>
> این دو تصمیم جدا هستند و در بیشتر مواقع **فقط اولی لازم است**. Downgrade دیتابیس، تاریخچه
> مالی را از دست می‌دهد؛ برگرداندن برنامه، چیزی را از دست نمی‌دهد.

---

## دو نوع بازگشت

| | بازگشت برنامه | بازگشت Migration |
|---|---|---|
| چه چیزی برمی‌گردد | کد در حال اجرا | Schema دیتابیس |
| از دست می‌رود | هیچ | داده‌ای که فقط در Schema جدید جا دارد |
| سرعت | ثانیه | دقیقه، با ریسک |
| برگشت‌پذیر | بله | نه همیشه |
| چند وقت یک‌بار لازم است | اغلب | به‌ندرت |

---

## ۱. بازگشت برنامه — گزینه پیش‌فرض

```bash
# کامیت قبلی تأییدشده را مستقر کنید و برنامه را راه بیندازید
```

```
□ برنامه بالا آمد
□ Smoke test فقط‌خواندنی سبز است
□ دیتابیس دست‌نخورده ماند
```

> **چرا این معمولاً کافی است:** هر شش Revision این پروژه **افزایشی** هستند — ستون و Index و
> قید اضافه می‌کنند و چیزی را که نسخه قبلی لازم دارد برنمی‌دارند. یک نسخه قدیمی‌تر برنامه
> روی Schema جدید کار می‌کند؛ فقط از ستون‌های تازه استفاده نمی‌کند.

---

## ۲. بازگشت Migration — فقط با تصمیم صریح

**پیش از هر Downgrade، این سه را جواب دهید:**

```
□ دقیقاً چه چیزی خراب است که Downgrade حلش می‌کند؟
□ داده‌ای که فقط در Schema جدید جا دارد چه می‌شود؟
□ پشتیبانِ قبل از Migration در دسترس و آزموده است؟
```

اگر هرکدام بی‌جواب ماند، **Downgrade نکنید.**

```bash
cd backend
export FINANCE_MIGRATION_DSN="<owner-dsn>"
alembic downgrade <revision>
```

## ۳. رفتار امتناع نسخه 0006 — بدانید و انتظارش را داشته باشید

`0006` دو ستون افزود که Core با آن‌ها شناخته می‌شود:

```
host_snapshot_id       ← msp_snapshots.id
host_file_version_id   ← msp_file_versions.id
```

و ستون قدیمی `source_file_version_id` را **اختیاری** کرد، چون ردیفی که از هسته وارد می‌شود
معادلی برایش ندارد.

> ### `0006 → 0005` عمداً امتناع می‌کند
>
> اگر حتی **یک** ردیف `progress_snapshot_refs` با `source_file_version_id IS NULL` وجود
> داشته باشد، Downgrade با پیام روشن متوقف می‌شود و **هیچ تغییری نمی‌دهد**:
>
> ```
> Downgrade to 0005 refused: N progress_snapshot_refs row(s) have no source_file_version_id
> ```

**چرا این درست است:** بدون این محافظ، Downgrade سعی می‌کرد ستون قدیمی را دوباره اجباری کند،
به ردیف‌های خالی می‌خورد و **وسط کار** شکست می‌خورد — با دیتابیسی نیمه‌تغییریافته. الان یا
کامل انجام می‌شود یا اصلاً شروع نمی‌شود.

**آزموده‌شده روی PostgreSQL 18:**

```
0006 → 0005 با یک ردیف وارد‌شده از هسته  →  REFUSED
نسخه بعدش                                →  0006  (تغییر نکرد)
ردیف آزمایشی                             →  دست‌نخورده
host_snapshot_id / host_file_version_id  →  دست‌نخورده
هر دو Index                              →  دست‌نخورده
```

**اگر واقعاً باید به 0005 برگردید** و ردیف‌های وارد‌شده از هسته دارید: یک تصمیم داده‌ای است،
نه یک تصمیم Migration. باید تکلیف آن ردیف‌ها روشن شود — و پاک‌کردنشان یعنی از دست‌دادن
ارتباط گزارش‌های مالی با Snapshotهایی که بر مبنایشان صادر شده‌اند.

## ۴. آنچه هرگز خودکار نمی‌شود

| ممنوع در اسکریپت استقرار | چرا |
|---|---|
| `alembic downgrade` | یک Pipeline نمی‌تواند تصمیم بگیرد که از دست‌دادن داده قابل قبول است |
| `alembic stamp` | نسخه را عوض می‌کند بدون تغییر Schema — بدترین حالت: دیتابیس درباره خودش دروغ می‌گوید |
| Downgrade خودکار وقتی Health check رد شد | Health check نمی‌داند مشکل از Schema است یا نه |
| بازگرداندن پشتیبان بدون تأیید انسانی | هر نوشتنی بعد از آن پشتیبان از بین می‌رود |

---

## ۵. معیار تصمیم — یک جدول

| نشانه | برنامه | دیتابیس |
|---|---|---|
| Migration خطا داد، تراکنش برگشت | ادامه ندهید | **دست نزنید** — Schema دست‌نخورده است |
| Migration موفق، برنامه خطا می‌دهد | ✅ برگردانید | ❌ نه |
| Migration موفق، اعتبارسنجی رد شد | صبر کنید | **اول بفهمید چه چیزی نمی‌خواند** |
| داده اشتباه نوشته شده | برگرداندن کمکی نمی‌کند | بازیابی پشتیبان، با تأیید |
| کندی شدید بعد از استقرار | ✅ برگردانید | ❌ نه |

---

## ۶. حفظ تاریخچه مالی

تصمیم بازگشت روی Production باید این‌ها را حفظ کند:

```
□ فاکتورهای تأییدشده و ردیف‌هایشان
□ گزارش‌های رسمی صادرشده و متن منجمدشان
□ ارجاع‌های Snapshot پیشرفت — که گزارش‌ها به آن‌ها Pin شده‌اند
□ نسخه‌های قیمت
□ رویدادهای ممیزی
```

> یک گزارش مالی رسمی باید همیشه بتواند بگوید بر چه مبنایی صادر شده. بازگشتی که آن مبنا را
> پاک کند، گزارش را به عددی بدون پشتوانه تبدیل می‌کند — حتی اگر خود گزارش سر جایش بماند.
