# کاشت آزمایشی منابع و تخصیص‌های MSP

**`TEST_ONLY` · `NON_PRODUCTION` · `MANUAL_EXECUTION_ONLY`**

---

## این ابزار parser نیست و نباید بشود

مسیر تولید این است:

```
فایل MPP  →  importer واقعی Core (MPXJ)  →  msp_resources · msp_resource_assignments
```

آن importer روی JVM اجرا می‌شود (`parser_engine` می‌گوید `mpxj-16.4.1/jvm-17`) و **بیرون از
این مخزن** است. هنوز پیدا نشده، و تا وقتی پیدا نشود دو جدول تازه خالی می‌مانند.

این اسکریپت آنها را از یک فایل **JSON** پر می‌کند تا سمت مالی همین حالا قابل آزمون باشد.
**نمی‌تواند فایل MPP باز کند**، به MPXJ یا JVM وابسته نیست، و در هیچ مسیر استقراری نیست.

> این محدودیت عمدی است. یک importer دوم و راحت داخل مالی، بی‌سر و صدا تبدیل به importer
> اصلی می‌شود.

---

## دو مرحله

### ۱ — ساخت fixture (بیرون از این مخزن)

استخراج‌کننده در scratchpad است، نه در `backend/`. اگر آن را اینجا می‌گذاشتیم، مالی به
MPXJ و یک JVM وابسته می‌شد — همان چیزی که معماری صریحاً ممنوع کرده.

```
scratchpad/extract_msp_fixture.py   →   bridge_fixture.json
```

### ۲ — کاشت (این اسکریپت)

```bash
cd backend

# پیش‌فرض: DRY RUN — هیچ نوشتنی
python -m scripts.test_only.seed_msp_resource_assignments \
    --dsn postgresql://.../bambo_finance_local \
    --snapshot-id 40 \
    --fixture /path/to/bridge_fixture.json

# نوشتن
... --apply

# کاشت دوباره روی همان snapshot
... --apply --replace-test-data
```

## نگهبان‌ها

| | |
|---|---|
| **DRY RUN پیش‌فرض** | بدون `--apply` هیچ‌چیز نوشته نمی‌شود |
| `bambo` و `bambo_finance_dev` | **پیش از اتصال** رد می‌شوند |
| `bambo_canonical_local` | `--allow-central` لازم دارد، **پیش از اتصال** بررسی می‌شود |
| هدف واقعی | از خودِ سرور پرسیده می‌شود، نه از DSN |
| snapshot ناموجود | امتناع |
| `task_uid` بیرون از این snapshot | امتناع — کلید خارجی‌ای نیست که این را بگیرد |
| `resource_uid` بیرون از fixture | امتناع |
| UID تکراری (منبع یا تخصیص) | امتناع |
| مقدار بدون واحد | امتناع |
| ردیف موجود روی این snapshot | امتناع، مگر با `--replace-test-data` |

**نگهبان دیتابیس مرکزی دو بار بررسی می‌شود** — یک بار روی نام DSN پیش از اتصال، یک بار از
خودِ سرور بعد از آن. DSN فقط یک ادعاست، ولی نگهبانی که فقط بعد از اتصال کار کند، وقتی سرور
در دسترس نیست اصلاً شلیک نمی‌کند و «هنگ کرد» امتناع نیست.

## آنچه هرگز نمی‌کند

**مقدار نمی‌سازد.** مقداری که در fixture نیست `NULL` نوشته می‌شود — نه صفر، و نه مشتق از
`Work`، `Duration` یا درصد.

**منبع WORK را طبقه‌بندی نمی‌کند.** MSP تفکیک labor از equipment ندارد، پس
`bambo_resource_type` برای آنها `NULL` می‌ماند.

**به `msp_tasks`، `msp_snapshots` یا `msp_file_versions` دست نمی‌زند.** آنها را برای
اعتبارسنجی می‌خواند و در هیچ‌کدام نمی‌نویسد.

---

## یک قرارداد در استخراج‌کننده که باید بدانید

MS Project فیلدهای *Actual* را با صفر مقداردهی اولیه می‌کند و راهی برای تفکیک «صفرِ
اندازه‌گیری‌شده» از «هرگز وارد نشده» ندارد. در فایل پل، هر ۷۲۷ تخصیص `Actual Material = 0`
دارند چون برنامه‌ریز هیچ پیشرفت مصالحی وارد نکرده.

نوشتن آن صفرها به مالی می‌گفت **۷۲۷ فعالیت اندازه‌گیری شدند و هیچ مصرفی نداشتند** — یک
اندازه‌گیری قاطع و غلط روی هر خط. استخراج‌کننده آنها را «گزارش‌نشده» ثبت می‌کند، که به
`unavailable` می‌رسد و همان چیزی است که واقعیت دارد.

**این یک قرارداد اعلام‌شده است، نه استنتاج پنهان.** یک صفرِ واقعاً اندازه‌گیری‌شده هم اینجا
قابل تشخیص نبود، و از دست دادنش خطای ارزان‌تری است.

## نتیجهٔ آزمون محلی

fixture واقعی از `زمان بندی پل.mpp`، روی PostgreSQL 18 یک‌بارمصرف:

```
۸۰ منبع (MATERIAL=۶۲ · WORK=۱۸)  ·  ۷۲۷ تخصیص  ·  ۱۲ بدون منبع
۲۸۹ تخصیص با مقدار برنامه‌ریزی‌شده  ·  ۰ با مقدار اجراشده

VERIFY UID تکراری             منبع=۰ تخصیص=۰
VERIFY ارجاع شکسته             فعالیت=۰ منبع=۰
VERIFY مقدار بدون واحد         ۰
VERIFY مقدار منبع در برابر جمع تخصیص‌ها   matching=۶۲ mismatched=۰
```

آن سطر آخر مهم است: **هر ۶۲ منبع MATERIAL، مقدار Resource Sheet‌شان دقیقاً برابر جمع
مقادیر تخصیص‌هایشان است.** یعنی نه ردیفی گم شده و نه تکرار شده.

## اجرای مرکزی — فقط دستی

```bash
# ۱. تأیید کنید کجا هستید
psql -c "SELECT current_database();"     # باید bambo_canonical_local باشد

# ۲. DRY RUN — خروجی کامل را بخوانید
python -m scripts.test_only.seed_msp_resource_assignments \
    --dsn "$FINANCE_CORE_DSN" --snapshot-id <id> \
    --fixture bridge_fixture.json --allow-central

# ۳. فقط پس از تصمیم انسانی
... --allow-central --apply
```

**این را خودکار نکنید.** داده آزمایشی است و روی دیتابیس مرکزی می‌نشیند؛ اگر بعداً importer
واقعی همان snapshot را پر کند، این ردیف‌ها باید اول با `--replace-test-data` یا با حذف دستی
برداشته شوند.
