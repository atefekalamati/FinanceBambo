# نقشهٔ فیلدهای MPP — خوانده‌شده از فایل، نه حدس‌زده

منبع: `inspect_mpp_fields.py` روی `Sources/test_progress.mpp`.
**هیچ کدی، schema یا mapping تغییر نکرده.** این سند فقط گزارش است.

> ### اصلاح — فایل عوض شد
>
> نسخهٔ اول این سند گفت «هیچ فیلد پیشرفتی پر نیست». آن **برای فایلی که آن لحظه روی دیسک
> بود درست بود** (۱٬۴۵۸٬۱۷۶ بایت، `sha256=55889b81…`). فایل ساعت ۱۰:۴۷ عوض شد
> (۱٬۶۳۸٬۴۰۰ بایت، `sha256=b86b6373…`) و نسخهٔ جدید **پیشرفت واقعی دارد**.
>
> اعداد زیر از نسخهٔ جدید است. جدول «ستون‌های تغییرنام‌یافته» عوض نشده — نام ستون‌ها
> همان است؛ آنچه عوض شد این است که حالا پر شده‌اند.

## پیشرفت در نسخهٔ جدید — هم استاندارد، هم Custom

| فیلد | تسک‌های غیرصفر |
|---|---|

**نکتهٔ مهم برای mapping:** برنامه‌ریز هم ستون‌های استاندارد و هم Custom را پر کرده.
یعنی parser فعلی که `percent_complete` را می‌خواند **کار می‌کند** — دیگر
`tasks with percent > 0 = 0` نیست، ۱۸۷ است. پس **هیچ تغییر mapping لازم نیست.**
`Number10`/`Number14` تکرار همان اطلاعات‌اند و خواندنشان چیزی اضافه نمی‌کند.

وقتی برنامه‌ریز ستونی به نام «ضریب وزنی زمانی» می‌سازد، در واقع یکی از خانه‌های آمادهٔ
MS Project (مثلاً `Number17`) را تغییر نام می‌دهد، و MS Project این نام را **در خود فایل**
ذخیره می‌کند. MPXJ آن را با `getCustomFields()` می‌دهد. یعنی این نگاشت **خوانده شده**،
نه حدس زده — که مهم است، چون حدس زدن بین بیست فیلد `Number` دقیقاً همان‌جور اشتباهی است
که یک عدد غلط را وارد گزارش مالی می‌کند.

## یک تأیید جانبی

`Text1` اسمش **«تاریخ شروع»** است. این مستقلاً همان چیزی را تأیید می‌کند که در کار قبلی
پیدا شد: `Text1` تاریخ نگه می‌دارد، نه کد فعالیت. سیم‌کشی `devhost/app.py` که
`("outline_number", "wbs")` را می‌دهد، درست است — و حالا دلیلش از خود فایل خوانده می‌شود
نه از روی شکل مقادیر.

## آیا mapping باید عوض شود؟ — نه

`coreint/progress.py` این‌طور می‌خواند:

```python
def task_progress(task):
    physical = task["physical_percent_complete"]
    duration = task["percent_complete"]
    ...
```

در نسخهٔ جدید فایل، `PERCENT_COMPLETE` روی **۱۸۷ تسک** پر است، پس این کد همین حالا کار
می‌کند. `PHYSICAL_PERCENT_COMPLETE` صفر است و قاعدهٔ «فیزیکیِ صفر جای خود را به مدت
می‌دهد» دقیقاً همین حالت را پوشش می‌دهد. **هیچ تغییری لازم نیست.**

`Number10`/`Number14` همان اطلاعات را تکرار می‌کنند؛ خواندنشان چیزی اضافه نمی‌کند و یک
مسیر دوم می‌سازد که می‌تواند با اولی اختلاف پیدا کند.

## یک شکاف که باقی می‌ماند (وزن‌ها، نه پیشرفت)

1. **Core بیشتر این فیلدها را اصلاً ذخیره نمی‌کند.** `msp_tasks` فقط شش ستون دارد:
   `number1, number3, number4, number13, number14, number18`. مقایسه با آنچه این فایل
   پر کرده:

   | | |
   |---|---|
   | پر است ولی Core ذخیره نمی‌کند | `Number5` (WF ریالی)، `Number6` (WF فیزیکی)، `Number12` (درصد وزنی)، `Number16` (آحجام هرآیتم)، **`Number17` (ضریب وزنی زمانی)**، `Number19` (ضریب وزنی مبنا) |
   | Core ذخیره می‌کند ولی در این فایل خالی است | `Number13` (پیشرفت فیزیکی)، `Number14` (پیشرفت واقعی) |

   یعنی **شش تا از ده فیلد پرشده در مسیر Core از بین می‌روند** — از جمله همان «ضریب وزنی
   زمانی» که پرسیدید. و دو ستونی که Core نگه می‌دارد، دقیقاً همان‌هایی‌اند که خالی‌اند.
   انتخاب ستون‌های Core برای برنامه‌ای بوده که پیشرفت را در ۱۳/۱۴ می‌نویسد؛ این فایل
   آن‌طور کار نمی‌کند.

   این شکافی است که باید با **تیم Core** حل شود، نه با یک مهاجرت مالی — `msp_tasks` مال
   Core است. `Number10` (درصد پیشرفت واقعی) هم ستونی در Core ندارد.
2. اگر روزی وزن‌ها لازم شدند، مسیرش همان الگوی `activity_code_fields` است: یک ترتیب
   پیش‌فرض در `coreint`، و میزبان در `devhost/app.py` قرارداد برنامه‌ریزانش را اعلام
   می‌کند. ولی اول باید ستون Core وجود داشته باشد.

برای **پیشرفت** این شکاف مطرح نیست: پیشرفت در ستون‌های استانداردی است که Core از قبل
ذخیره می‌کند.

## هشدار

وزن (`ضریب وزنی`) **پیشرفت نیست**. وزن می‌گوید یک کار چقدر از پروژه است؛ پیشرفت می‌گوید
چقدرش انجام شده. اگر `Number17` به‌عنوان درصد پیشرفت خوانده شود، هر کاری ۹۹.۹٪ کامل
گزارش می‌شود در حالی که هیچ‌کاری شروع نشده. `inspect_mpp_fields.py` این دو را با
`classify()` جدا نگه می‌دارد دقیقاً به همین دلیل.
