# قرارداد میزبان — آنچه BAMBO باید فراهم کند

ماژول مالی داخل میزبان BAMBO اجرا می‌شود و چیزی از خودش نمی‌سازد که میزبان صاحبش باشد:
هویت، عضویت، مجوز، کاتالوگ فعالیت‌ها و فضای ذخیرهٔ فایل همه از میزبان می‌آیند.

این سند فهرست دقیق آن‌هاست. هر بندی که انجام نشود، یک رفتار مشخص را از کار می‌اندازد و
این‌جا نوشته شده که کدام را.

---

## ۱. دیتابیس

| چیز | مقدار |
|---|---|
| موتور | PostgreSQL ۱۶ (روی ۱۶٫۱۵ آزموده شد) |
| نقش سرویس | فقط `SELECT/INSERT/UPDATE/DELETE` — **بدون اجازهٔ DDL** |
| نقش مهاجرت | مالک schema، فقط در گام مهاجرت استفاده می‌شود |

جداسازی این دو نقش عمدی است: سرویس در حال اجرا نباید بتواند schema را عوض کند. نمونهٔ
دستورهای ساخت نقش در `.env.example` آمده است.

**ماژول مالی جدول‌های Core را نمی‌سازد.** مهاجرت ۰۰۰۹ به `msp_tasks` کلید خارجی دارد و
اگر آن جدول نباشد، با پیام صریح متوقف می‌شود. روی دیتابیس مشترک BAMBO، Core آن را می‌سازد.

## ۲. ثبت مجوزها — **این بند بلوک‌کننده است**

ماژول این مجوزها را می‌خواند:

| کد مجوز | برای چه |
|---|---|
| `finance.view` | دیدن داده‌های مالی |
| `finance.edit` | ویرایش برآورد، قیمت، تبدیل واحد |
| `finance.manage_invoice` | **ساخت، تأیید، ابطال و اصلاح فاکتور** |
| `finance_report.view` | دیدن گزارش‌ها |
| `finance_report.export` | خروجی گرفتن |
| `finance_report.issue` | صدور گزارش منجمد |

**اندازه‌گیری شد:** روی نسخهٔ فعلی کاتالوگ، **`finance.manage_invoice` ثبت نشده است**.
تا وقتی ثبت نشود هیچ‌کس نمی‌تواند آن را داشته باشد، و **کل جریان فاکتور برای همه ۴۰۳
می‌دهد**. این تنها پیش‌نیازی است که یک جریان کاری کامل را متوقف می‌کند.

شکل ردیف، از روی خودِ جدول شما:

```sql
INSERT INTO permissions (module_key, action_key, code, label, group_name)
VALUES ('finance', 'manage_invoice', 'finance.manage_invoice',
        'مدیریت فاکتور مالی', 'امور مالی');
```

سپس آن را به نقشی که باید فاکتور بزند اعطا کنید (نقش یا override، هر کدام که رویهٔ شماست).

**چرا جدا از `finance.edit`:** کسی که برآورد را ویرایش می‌کند لزوماً نباید بتواند پول را
از در بیرون بفرستد. این جداسازی آزموده شده: همان هویت با همان `finance.edit` ولی بدون
`finance.manage_invoice` پاسخ ۴۰۳ می‌گیرد.

## ۳. احراز هویت

ماژول **خودش احراز هویت نمی‌کند**. یک تابع از میزبان می‌گیرد که نشست جاری را برمی‌گرداند.

| نکته | وضعیت |
|---|---|
| نوع نشست | **کوکی‌محور** |
| هدر `Authorization` | خوانده **نمی‌شود** |
| توکن CSRF | لازم **نیست** |
| نشست نامعتبر یا منقضی | باید **۴۰۱** بدهد، **نه ۳۰۲** |

۴۰۱ و ۴۰۳ عمداً از هم جدا شده‌اند: رابط کاربری ۴۰۱ را «نشست تمام شد» می‌خواند و کل صفحه
را با صفحهٔ ورود جایگزین می‌کند؛ ۴۰۳ یعنی «وارد شده‌اید ولی مجوز ندارید». اگر میزبان به‌جای
۴۰۱ یک redirect بدهد، کاربرِ خارج‌شده پیام «دسترسی ندارید» می‌بیند.

**هیچ ماژولی در `app/` و `coreint/` هیچ هدر درخواستی نمی‌خواند** — این با آزمون تثبیت شده،
تا هدر آزمونی نتواند در تولید جای کسی را بگیرد.

## ۴. شناسهٔ پروژه و سازمان

مسیرها `projectId` می‌گیرند و ماژول آن را به همان چیزی می‌دهد که میزبان برای بررسی عضویت
لازم دارد. شناسهٔ پروژه **رشته** است (مثلاً `terrace`)، نه UUID. سازمان از نشست می‌آید.

چهار دروازه به‌ترتیب اجرا می‌شوند و ترتیبشان بخشی از تضمین است:

```
احراز هویت  →  عضویت سازمان  →  عضویت پروژه  →  مجوز
```

اگر مجوز پیش از احراز هویت پرسیده شود، به کاربرِ خارج‌شده ۴۰۳ داده می‌شود به‌جای صفحهٔ ورود.

## ۵. کاتالوگ فعالیت‌ها و ترتیب نسخهٔ زمان‌بندی

گزارش‌های WBS، ردیف‌های برآورد را از طریق **کد فعالیت** به مرحله می‌رسانند. کاتالوگ فعالیت
از نسخهٔ فعال فایل زمان‌بندی ساخته می‌شود.

**یک قرارداد باز:** «نسخهٔ فعال» امروز یعنی تازه‌ترین نسخهٔ `ready` بر اساس زمان import.
زمانِ import، **ترتیب کسب‌وکاری** را ثابت نمی‌کند — فایلی که دیرتر وارد شده لزوماً نسخهٔ
جدیدتر برنامه نیست. اگر میزبان مفهومی برای «نسخهٔ رسمی برنامه» دارد، باید آن را اعلام کند.
تا آن موقع، ترتیب همان ترتیب import می‌ماند و این در `KNOWN_LIMITATIONS_FA.md` باز است.

## ۶. فایل زمان‌بندی (MPP)

| متغیر | معنی |
|---|---|
| `MPP_IMPORT_ENABLED` | تا `true` نباشد هیچ import انجام نمی‌شود |
| `MPP_IMPORT_ROOT` | ریشهٔ ذخیرهٔ تأییدشده؛ **پیش‌فرض ندارد** |
| `MPP_JAVA_HOME` | یک JRE 17 برای MPXJ |
| `MPP_MAX_FILE_SIZE_MB` | سقف اندازهٔ فایل، پیش‌فرض ۱۰۰ |
| `MPP_IMPORT_INTERVAL_MINUTES` | دورهٔ بررسی تغییر؛ خالی یعنی بدون بررسی دوره‌ای |

فایل با مسیر `<MPP_IMPORT_ROOT>/<projectId>.mpp` خوانده می‌شود. **هیچ دایرکتوری به‌صورت
یکجا import نمی‌شود** و فایلی که نامش یک پروژهٔ مالی نیست رد می‌شود. مسیر باید یک مسیر
فایل‌سیستم باشد؛ object storage پشتیبانی نمی‌شود.

**خواندن روی یک کپی خصوصی انجام می‌شود:** فایل به یک دایرکتوری موقت کپی، دوباره hash، و از
روی کپی خوانده می‌شود. اگر hash کپی با آنچه انتخاب شده فرق کند، import رد می‌شود. این جلوی
فایلی را می‌گیرد که وسط خواندن عوض شده باشد.

## ۷. ذخیرهٔ پیوست مالی

پیوست‌ها (تصویر و صوت فاکتور) در فضای ذخیرهٔ میزبان می‌نشینند. ماژول **قلاب پویش بدافزار**
را دارد و جایش مشخص است — پس از `validate_file` و پیش از `put` در
`services/attachments.py` — ولی خود پویش کار تیم Core است.

## ۸. تحلیل پس از رویداد

هیچ زمان‌بند داخلی‌ای وجود ندارد. اگر میزبان می‌خواهد پس از یک رویداد (مثلاً تأیید فاکتور
یا import تازه) تحلیلی اجرا شود، باید خودش آن را صدا بزند. ماژول هیچ صفی و هیچ worker ای
راه نمی‌اندازد.
