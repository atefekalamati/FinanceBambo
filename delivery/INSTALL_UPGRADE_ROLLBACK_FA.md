# نصب، ارتقا، و بازگشت

همهٔ دستورها از دایرکتوری `backend/` اجرا می‌شوند مگر خلافش گفته شود.

---

## ۰. پیش از هر چیز: پشتیبان

```bash
pg_dump -h <host> -U <owner> -d <database> --format=custom \
        --file backup-$(date +%%F-%%H%%M).dump
```

**نسخهٔ ابزار را با نسخهٔ سرور یکی کنید.** ابزار جدیدتر روی سرور قدیمی‌تر تنظیماتی می‌فرستد
که سرور نمی‌شناسد و بازگردانی خطا می‌دهد — ما دقیقاً همین را دیدیم: `pg_restore` نسخهٔ ۱۸
روی سرور ۱۶ پیام `unrecognized configuration parameter "transaction_timeout"` داد.

```bash
psql -c "SHOW server_version"      # نسخهٔ سرور
pg_dump --version                  # باید major یکسانی داشته باشد
```

## ۱. نصب تازه

```bash
# ۱. دیتابیس خالی
createdb -h <host> -U <owner> <database>

# ۲. جدول‌های Core باید موجود باشند (مهاجرت ۰۰۰۹ به msp_tasks وابسته است)

# ۳. مهاجرت‌ها، با نقش مالک
export FINANCE_MIGRATION_DSN=postgresql://<owner>:<pass>@<host>/<database>
python -m alembic upgrade head

# ۴. بررسی
python -m alembic current          # باید 0020 باشد
```

**آزموده شد:** زنجیرهٔ کامل ۰۰۰۱ تا ۰۰۲۰ روی یک دیتابیس خالی، ۷ بررسی ساختاری پاس.

## ۲. ارتقا از نسخهٔ قبلی

```bash
export FINANCE_MIGRATION_DSN=postgresql://<owner>:<pass>@<host>/<database>
python -m alembic current          # از کجا شروع می‌کنیم
python -m alembic upgrade head
python -m alembic current          # 0020
```

**آنچه ۰۰۲۰ با فاکتورهای موجود می‌کند — اندازه‌گیری‌شده روی ۵۳ فاکتور که ۴۵ تای‌شان
صادرشده بودند:**

| چیز | نتیجه |
|---|---|
| تعداد فاکتورها | بدون تغییر |
| `invoice_number` (شمارهٔ صادرشده) | **بایت‌به‌بایت دست‌نخورده** |
| مبالغ مالی | بدون تغییر |
| رکوردهای ممیزی | بدون تغییر |
| payload گزارش‌های منجمد | بدون تغییر |
| ستون تازهٔ `invoice_seq` | به هر فاکتور بر اساس ترتیب ساخت داده می‌شود |
| `finance_invoice_counters` | ساخته و از بیشترین شماره + ۱ مقداردهی می‌شود |

**تریگر تغییرناپذیری.** backfill یک `UPDATE` است و `confirmed_invoice_immutable` هر
UPDATE روی فاکتور صادرشده را رد می‌کند. تریگر **در طول همان یک تراکنش** غیرفعال و دوباره
فعال می‌شود. اگر مهاجرت وسط کار شکست بخورد، rollback تریگر را هم برمی‌گرداند — آزموده شد:
داخل تراکنش `D`، پس از rollback دوباره `O`، بدون هیچ گام دستی.

**اجرای دوباره بی‌خطر است:** `alembic upgrade head` روی دیتابیسی که همین حالا ۰۰۲۰ است هیچ
کاری نمی‌کند و هیچ شماره‌ای عوض نمی‌شود.

## ۳. بازگشت (downgrade) — **با محدودیت واقعی**

```bash
python -m alembic downgrade 0019
```

**چه چیزی برمی‌گردد:**

| چیز | وضعیت |
|---|---|
| همهٔ فاکتورها | **سالم می‌مانند** |
| شماره‌های صادرشده (`invoice_number`) | **بدون تغییر** |
| مبالغ، ممیزی، گزارش‌های منجمد | **بدون تغییر** |

**چه چیزی از دست می‌رود و برنمی‌گردد:**

- ستون `invoice_seq` **حذف می‌شود**. شماره‌های تخصیص‌یافته پاک می‌شوند.
- جدول `finance_invoice_counters` **حذف می‌شود**.

**ارتقای دوباره، بازیابی نیست.** اگر دوباره به ۰۰۲۰ بروید، شماره‌ها **از نو از روی
`created_at` مشتق می‌شوند**. روی جدولی که بین دو اجرا تغییر نکرده، همان اعداد قبلی درمی‌آید
— ولی اگر در این فاصله فاکتوری اضافه شده باشد، یا دو فاکتور دقیقاً هم‌زمان ساخته شده باشند،
**اعداد متفاوت خواهند بود**. هیچ‌جا شماره‌های قبلی نگه داشته نمی‌شود.

**نتیجهٔ عملی:** downgrade برای برگرداندن schema امن است، و برای برگرداندن *شماره‌ها* نیست.
اگر شماره‌ها جایی بیرون از سیستم استفاده شده‌اند، پیش از downgrade از دیتابیس پشتیبان
بگیرید و بازیابی را از آن پشتیبان انجام دهید، نه از downgrade.

## ۴. بازگردانی از پشتیبان

فایل `bambo_finance_candidate.dump` **جداگانه** تحویل می‌شود.

```bash
createdb -h <host> -U <owner> <new-empty-database>
pg_restore -h <host> -U <owner> -d <new-empty-database> \
           --exit-on-error --no-owner --no-privileges bambo_finance_candidate.dump
echo $?      # باید ۰ باشد
```

`--exit-on-error` یعنی اولین خطا کار را متوقف می‌کند، به‌جای اینکه خطی در یک لاگ بماند که
کسی نمی‌خواند. **کد خروجی را از خود `pg_restore` بخوانید**، نه از انتهای یک لولهٔ دستوری.

**این یک ادغام نیست.** این تصویر کامل یک دیتابیس است. بازگرداندنش روی دیتابیسی که داده
دارد، آن داده را جایگزین می‌کند. برای محیط بازبینیِ **تازه** ساخته شده است.

## ۵. بررسی سلامت پس از نصب

```bash
# ۱. مهاجرت‌ها در جای درست
python -m alembic current                      # 0020

# ۲. ناوردهای مالی
python scripts/verify_finance_invariants.py --dsn <dsn>
#    انتظار: 0 failed, 21 passed

# ۳. قرارداد API هم‌گام با کد
python scripts/export_openapi.py --check

# ۴. سرویس بالا می‌آید و پاسخ می‌دهد
curl -s -o /dev/null -w "%%{http_code}" http://<host>:<port>/
```

## ۶. پشتیبان‌گیری دوره‌ای

| چه چیزی | چرا |
|---|---|
| کل دیتابیس، custom format | جدول‌های مالی به Core وابسته‌اند و جدا معنا ندارند |
| پیش از **هر** مهاجرت | downgrade شماره‌ها را برنمی‌گرداند |
| فضای ذخیرهٔ پیوست‌ها | در dump نیست؛ فایل‌ها بیرون دیتابیس‌اند |

هر پشتیبان را **یک‌بار بازگردانی کنید** تا بدانید کار می‌کند. پشتیبانی که آزموده نشده، یک
فرض است نه یک پشتیبان.
